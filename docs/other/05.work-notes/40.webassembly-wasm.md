## 1\. Why does WebAssembly “look dangerous” in terms of security? {#一、为什么-webassembly-在安全上-看起来很危险}

Make an intuitive judgment first:

| Features | Security Risks |
| ------ | ------ |
| Close to native speed | Similar to native code |
| Explicit memory | Easy to cross boundaries |
| Can be compiled | Difficult to statically analyze |
| Often from third parties | Supply chain risks |

👉 **If Wasm can access the system at will, browser security will crash directly**

So:

> **Wasm was designed from the beginning to be "caged native code"**


## 2\. The overall security position of Wasm in Chrome {#二、chrome-中-wasm-的整体安全位置}

```
操作系统
  ↑
Chrome OS Sandbox
  ↑
Renderer Process
  ↑
V8 Wasm Engine
  ↑
WebAssembly Module
```

👉 Wasm **does not have higher permissions**
👉 It is just an execution engine in **Renderer**


## 3\. The first line of defense: process-level isolation (Chrome) {#三、第一道防线-进程级隔离-chrome}

### 1️⃣ Where is Wasm running? {#_1️⃣-wasm-跑在哪}

* **Renderer Process**
* Same level as JS
* Protected by **Site Isolation**

```text
bank.com Wasm → Renderer A
evil.com Wasm → Renderer B
```

Even if Wasm is compromised:

* Cannot cross site
* Can't access OS


### 2️⃣OS-level sandbox {#_2️⃣-os-级沙箱}

Renderer process:

* Cannot read or write arbitrary files
* Cannot call system API
* Unable to execute system commands

👉 **Wasm has no concept of "system call"**


## 4\. The second line of defense: Wasm’s language-level security model ⭐⭐⭐⭐⭐ {#四、第二道防线-wasm-的语言级安全模型-⭐⭐⭐⭐⭐}

This is the **core security point** of Wasm.


### 1️⃣ There is no “arbitrary pointer” {#_1️⃣-没有-任意指针}

```c
int* p = (int*)0xdeadbeef; // ❌ Wasm 中不存在
```

Wasm：

* Only **Linear Memory**
* address = offset


### 2️⃣ Linear memory model {#_2️⃣-线性内存模型}

```
Linear Memory
 ├── 0x0000
 ├── ...
 ├── 0x10000
```

Linear-memory accesses must respect overall memory bounds:

* Out-of-range accesses trap; checks or guard pages can enforce the semantics.
* Adjacent objects within the region can still be overwritten; C/C++ buffer bugs and use-after-free do not vanish.

👉 **Host isolation is not object-level application memory safety**.
👉 **Valid instructions cannot arbitrarily access Renderer memory or the JS Heap; engine bugs are a separate risk**.


### 3️⃣ Non-executable data (W^X) {#_3️⃣-不可执行数据-w-x}

* Wasm memory ≠ executable
* Separation of Code Space and Data Space

👉 Prevent:

* shellcode injection
* JIT spraying


### 4️⃣ Module verification (Validation) {#_4️⃣-模块验证-validation}

Wasm before execution:

* Verify bytecode first
* Control flow is legal
* correct type
* Stack balancing

```text
非法模块 → 拒绝加载
```


## 5\. The third line of defense: V8 Wasm engine {#五、第三道防线-v8-wasm-引擎}

### 1️⃣ Compilation process {#_1️⃣-编译流程}

```
Wasm Binary
  ↓
Decoder & Validator
  ↓
Liftoff（baseline compiler）
  ↓
TurboFan（优化编译）
```

#### security policy {#安全策略}

<span id="_2️⃣-边界检查永不移除-关键"></span>


* Compile quickly first
* Re-security optimization
* Can be rolled back at any time


### 2️⃣ Preserve linear-memory bounds semantics {#_2️⃣-保留线性内存边界语义}

Even after optimization:

* Out-of-bounds accesses must preserve trap semantics.
* Proven-safe accesses may eliminate redundant checks or use guard pages; the semantics do not mandate an explicit check on every access.


### 3️⃣ Interaction with JS is “controlled” {#_3️⃣-与-js-的交互是-受控的}

Wasm **cannot take the initiative**:

* Access DOM
* Make network request
* Call system API

Only:

```js
imported_function()
```

👉 JS is **Capability Broker**


## 6\. The fourth line of defense: Capability-based Security {#六、第四道防线-能力模型-capability-based-security}

> **Wasm itself has no abilities, the abilities come from the host**

#### Example {#举例}

```js
const wasm = new WebAssembly.Instance(module, {
  env: {
    log: console.log
  }
})
```

Wasm can only:

* Call `log`
* Cannot call `alert`
* Cannot access `document`

👉 This is **one of the strongest security models**


## 7\. Wasm vs JS: Who is more dangerous? {#七、wasm-vs-js-谁更危险}

| Dimension | JS | Wasm |
| ---- | ---------- | ------ |
| Memory model | No arbitrary-address syntax; engine bugs remain possible | Isolated linear memory without object-level safety; engine bugs remain possible |
| Execution permissions | Restricted by browser and host APIs | Restricted by host imports and browser policies |
| Performance | Depends on workloads and optimization | Suitable for some compute tasks; measure it |
| Attack surface | JS engine, DOM and host APIs | Wasm engine, imports and application logic |

Language names do not establish overall safety. Wasm protects host boundaries; applications still need safe languages, input checks and resource management.

[Official WebAssembly memory safety documentation](https://webassembly.org/docs/security/#memory-safety).


## 8\. What can Wasm attack?What can't be attacked? {#八、wasm-能攻击什么-不能攻击什么}

#### ❌ Can’t {#❌-不能}

* Bypass the same origin policy
* Access Cookies
* Manipulating the DOM
* Send a request directly
* Tuning system API

#### ⚠️ Possible risks {#⚠️-可能的风险}

* DoS (infinite loop)
* Specter side channel (mitigated)
* Engine implementation vulnerabilities; do not describe them as rare without a defined dataset.


## 9\. Wasm + CSP security strategy {#九、wasm-csp-安全策略}

```http
Content-Security-Policy:
  script-src 'self';
  object-src 'none';
```

⚠️ Wasm by:

* `script-src`
* `wasm-unsafe-eval` (new)

```http
script-src 'self' 'wasm-unsafe-eval';
```

👉 Default is stricter


## 10\. Real attack perspective (very important) {#十、真实攻击视角-非常重要}

#### Attack Chain (Extremely Hard) {#攻击链-极难}

```
恶意 Wasm
 ↓
V8 Wasm JIT bug
 ↓
突破 Wasm sandbox
 ↓
突破 Renderer sandbox
 ↓
OS
```

👉 Chrome security goals:

> **Make this chain almost unfeasible**


## 11\. The ultimate answer to "WebAssembly security model" {#十一、-webassembly-安全模型-终极答案}

> Browser WebAssembly is constrained by the same-origin policy, renderer sandbox and host capabilities. Validation and linear-memory bounds provide isolation without object-level safety. Imports grant host capabilities; application bugs, resource exhaustion and engine vulnerabilities remain relevant.
