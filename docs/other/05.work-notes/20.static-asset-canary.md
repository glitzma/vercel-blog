## 🔵 Canary Release for Static Assets {#🔵-静态资源灰度发布-canary-release-for-static-assets}

Static resources (HTML/CSS/JS/Images, etc.) have no server-side logic, so the core of grayscale publishing is:

> **Allow some users to access the new version of static resources, while other users still use the old version.**
> Key to implementation: **Diversion + version coexistence + rollback**

Here are some common possible solutions:


## ⭐ Option 1: Nginx / CDN offload (most commonly used and most stable) {#⭐-方案-1-nginx-cdn-分流-最常用、最稳定}

#### ⛳ Ideas {#⛳-思路}

1. **Build two static resources: old and new**
2. **Route some users to the new resource directory according to certain rules**
3. Rules can be: `IP`, `Cookie`, `Header`, `AB Test ID`, account, etc.


### 🔧 Nginx configuration example (split by cookie) {#🔧-nginx-配置示例-按-cookie-分流}

```nginx
# 默认走旧版本
set $version "v1";

# 如果 Cookie 中带 version=v2 则走灰度版本
if ($http_cookie ~* "version=v2") {
    set $version "v2";
}

location / {
    alias /var/www/$version/;  # 指向对应版本资源目录
    try_files $uri $uri/ /index.html;
}
```

#### Usage {#用法}

Set `Cookie` for grayscale users:

```bash
document.cookie = "version=v2; path=/"
```

#### Advantages {#优点}

✔ Accurately control user ratio
✔ Versions coexist and can be rolled back at any time
✔ Transparent to the front end and compatible with SPA


## ⭐ Solution 2: CDN edge rule grayscale (commonly used by enterprises, such as Alibaba Cloud and Cloudflare) {#⭐-方案-2-cdn-边缘规则灰度-企业常用-如阿里云、cloudflare}

CDN support:

* **Distribution by User-Agent**
* **Divided by region**
* **Split by Cookie**
* **Split by percentage (weight)**

#### Example (Cloudflare Worker/PHP Rule) {#示例-cloudflare-worker-php-rule}

```js
if (Math.random() < 0.1) {
  // 10% 用户访问新版本
  return fetch("https://cdn.xxx.com/app-v2" + request.url);
} else {
  return fetch("https://cdn.xxx.com/app-v1" + request.url);
}
```


## ⭐ Option 3: HTML Layer AB Test (for SPA) {#⭐-方案-3-html-层-ab-test-适用于-spa}

#### ⛳ Ideas {#⛳-思路-1}

Return different versions of index.html to different users, with different JS/CSS paths.

Example:

* `index.v1.html` -> Reference `/static/v1/*`
* `index.v2.html` -> Reference `/static/v2/*`

Nginx/Server decides which HTML to return to whom.


## ⭐ Solution 4: Single-page application internal version switching (limited scenario) {#⭐-方案-4-单页应用内部版本切换-有限场景}

Decide which version of resources to load in JS (less commonly used)

```js
if (isGrayUser()) {
  loadScript("/static/v2/main.js");
} else {
  loadScript("/static/v1/main.js");
}
```


## ⭐ Solution 5: `CI/CD` process grayscale {#⭐-方案-5-ci-cd-流程灰度}

Combined with scripts to automatically execute:

1. Upload `v2` static resources
2. `CDN / Nginx` set `x%` grayscale offloading
3. Monitoring indicator `OK` → Increase percentage → Full amount
4. If abnormal → switch back to `v1`


## 🔥Key points to note {#🔥-关键注意点}

### 1. **Must use build product with Hash** {#_1-必须使用带-hash-的构建产物}

For example:

* `main.55c33.js`
* `vendor.9ad01.css`

Otherwise caching will cause user version inconsistency.


### 2. **Old version resources must continue to be retained** {#_2-旧版本资源必须继续保留}

Otherwise, grayscale users will get `404` when refreshing the page.


### 3. **`index.html` is the key to grayscale** {#_3-index-html-才是灰度的关键}

CDN caching strategy must ensure:
**Page `（HTML）` Grayscale, static resources available `（JS/CSS）` Long-term caching.**

Most common configurations:

* `HTML`：`no-cache` or `max-age=0`
* `JS/CSS`：`cache-control: max-age=31536000, immutable`


### 🟢 Give you a very short and easy-to-remember summary {#🟢-给你一个非常简短易记的总结}

> Static resource grayscale = two versions coexist + control different users to return different `index.html`.
>
> Core: **HTML offloading, multi-version resource coexistence, cache version locking.**


Here is a **complete and realistic grayscale release case of static resources for a Vue project**.
Includes: build, multi-version deployment, `Nginx` configuration, `Cookie` grayscale offloading, rollback solution.

The content is very practical and can be explained directly in interviews.


## 🔵 Vue project static resource grayscale release (complete implementation case) {#🔵-vue-项目静态资源灰度发布-完整可落地案例}

### 📌 scene {#📌-场景}

Your project is:

```
my-app/
  dist/
    v1/     ← 当前线上版本
    v2/     ← 新灰度版本（准备发布）
```

Do you want:

* `10%` users access `v2`
* `90%` users continue to use `v1`
* Can be rolled back at any time
* Old version resources will continue to be retained to avoid `404`


### Step 1: Build the product for version isolation {#第一步-构建产物做版本隔离}

#### 🔧 `build` script (`package.json`) plus `version` parameter {#🔧-build-脚本-package-json-加-version-参数}

```json
{
  "scripts": {
    "build:v1": "vue-cli-service build --dest dist/v1",
    "build:v2": "vue-cli-service build --dest dist/v2"
  }
}
```

Execution:

```bash
npm run build:v1   # 线上的旧版本
npm run build:v2   # 即将灰度的新版本
```

In this way, Vue will be packaged separately:

* `/dist/v1/*`
* `/dist/v2/*`

And each `JS/CSS` has a `hash`, so there is no conflict.


### Step 2: Server Structure {#第二步-服务器结构}

Deploy two sets of versions to the server:

```
/var/www/my-app/
    v1/
    v2/
```

> ⚠ `index.html` cannot be cached, otherwise grayscale streaming will be invalid.


### Step 3: Nginx grayscale configuration (core) {#第三步-nginx-灰度配置-核心}

The following is the grayscale traffic configuration that can be used directly. Press `Cookie` to determine whether the user falls into `v1` or `v2`.


#### 🔧 `Nginx` configuration (can be copied directly) {#🔧-nginx-配置-可直接复制}

```nginx
# 给灰度用户设置 Cookie 后即可访问 v2
map $http_cookie $version {
    default "v1";
    "~*version=v2" "v2";
}

server {
    listen 80;
    server_name example.com;

    # 根路径
    location / {
        alias /var/www/my-app/$version/;

        # 关闭 index.html 缓存
        add_header Cache-Control "no-cache";

        try_files $uri $uri/ /index.html;
    }

    # 静态资源开启强缓存
    location ~* \.(js|css|png|jpg|jpeg|gif|svg)$ {
        alias /var/www/my-app/$version/;
        add_header Cache-Control "max-age=31536000, immutable";
    }
}
```

##### ✔ Description {#✔-说明}

📌 `version=v2` in `Cookie` → visit v2
📌 No `Cookie` → Default access v1
📌 `JS/CSS` never expires (with `hash`, no conflict)
📌 `HTML` is not cached for real-time offloading


### Step 4: Inject `Cookie` into grayscale users {#第四步-给灰度用户注入-cookie}

Method 1: Browser console test

```js
document.cookie = "version=v2; path=/";
```

Refresh → Force into `v2` version.


Method 2: The server issues `Cookie` to some users (real grayscale)

For example:

```nginx
# 随机 10% 灰度用户
set $rand "";
set $rand $request_id;

# 取 request_id 的最后一位数字
if ($rand ~ "([0-9])$") {
    set $last_digit $1;
}

# 0~9 的数字，10% 落入 v2
if ($last_digit = 1) {
    add_header Set-Cookie "version=v2; Path=/;";
}
```

For example, grayscale `Cookie` is issued to users with a `1` at the end.


### Step 5: Rollback plan (very important) {#第五步-回滚方案-非常重要}

##### ❌ Found a problem?One-click rollback: {#❌-发现问题-一键回滚}

Just change the offloading logic of `Nginx`:

1. **Modify `Nginx` diversion: all users go to `v1`**

   ```nginx
   map $http_cookie $version {
       default "v1";
   }
   ```
2. **`reload Nginx`**

   ```bash
   nginx -s reload
   ```
3. **Wait for all grayscale `Cookie` to expire or clear `Cookie` now**
4. **Confirm that there are no requests to access the `/v2/` directory (via `Nginx access log`)**
5. **Finally delete the `/v2/` directory**

Rollback is very fast because it is a purely static resource.


### Step 6: `CI/CD` automation (optional) {#第六步-ci-cd-自动化-可选}

For example:

1. `Jenkins / GitHub Actions` compile `v2`
2. Upload ` v2 ` to the server
3. Modify ` Nginx` The diversion ratio is from ` 1% → 5% → 10%`
4. Observe logs and alarms
5. Delete after full volume ` v1` (or keep 1 historical version)


### 🟢Final effect {#🟢-最终效果}

* Visit the same domain name
* Different users access different versions of `Vue ` Application
* Old resources are retained and can be rolled back at any time
* `index.html` dynamic grayscale, `JS/CSS ` permanent cache
* `Vue` project is completely non-intrusive



## 🔵 Grayscale automation script {#🔵-灰度自动化脚本}

The script starts with **`Nginx + Cookie` Diversion** For example, it can be used `Jenkins / GitHub Actions /` Performed manually.

Key features:

✔ Support setting grayscale ratio (such as `5%、10%、30%、50%、100%` ）
✔ Automatically write the `map` configuration of `Nginx`
✔ Automatic `reload Nginx`
✔ Automatic backup configuration (to prevent misoperation)
✔ Automatically turn off grayscale logic after full volume

This is a set of static resource grayscale control processes commonly used in the industry.


#### 🟦 1. `Nginx` offloading solution (based on random number grayscale) {#🟦-1-nginx-分流方案-基于随机数灰度}

You need to reserve a field in `Nginx` for different scripts to modify:

```nginx
# /etc/nginx/conf.d/gray.conf
map $cookie_gray $gray_flag {
    default "off"; # 可由脚本修改为 on/off
}

map $request_id $gray_bucket {
    "~(?<num>[0-9])$" $num;  # 取 request_id 的最后一位数字 (0-9)
}

map "$gray_flag:$gray_bucket" $version {
    # 灰度开关关闭 → 全量旧版本
    "off:0"  "v1";
    "off:1"  "v1";
    "off:2"  "v1";
    "off:3"  "v1";
    "off:4"  "v1";
    "off:5"  "v1";
    "off:6"  "v1";
    "off:7"  "v1";
    "off:8"  "v1";
    "off:9"  "v1";

    # 灰度开关开启 → 实际灰度逻辑由脚本注入
    # (脚本会把 gray.conf 的内容替换成对应灰度比例)
}
```

The script just needs to be modified **Mapping table corresponding to gray scale** 。


#### 🟦 2. Grayscale script gray.sh (supports any ratio of 0–100%) {#🟦-2-灰度脚本-gray-sh-支持-0–100-任意比例}

Create file:

```
/opt/scripts/gray.sh
```

The content is as follows (can be used directly):

```bash
#!/bin/bash

# -----------------------------
# 参数检查
# -----------------------------
if [ -z "$1" ]; then
    echo "❌ 使用方法: ./gray.sh <比例>"
    echo "   示例: ./gray.sh 10   # 灰度 10%"
    echo "   示例: ./gray.sh 100  # 全量"
    exit 1
fi

PERCENT=$1

if [ "$PERCENT" -lt 0 ] || [ "$PERCENT" -gt 100 ]; then
    echo "❌ 灰度比例必须是 0~100"
    exit 1
fi

# -----------------------------
# 配置文件位置
# -----------------------------
NGINX_GRAY_CONF="/etc/nginx/conf.d/gray.conf"
BACKUP="/etc/nginx/conf.d/gray.conf.bak"

# 备份配置
cp $NGINX_GRAY_CONF $BACKUP

# -----------------------------
# 生成新的灰度映射规则
# -----------------------------
echo "⚙ 正在更新灰度比例为：${PERCENT}% ..."

# 计算有多少 bucket 命中灰度
# bucket 0~9，一共 10
GRAY_BUCKET_COUNT=$((PERCENT / 10))

# 处理小数，如 15% → 灰度 1 个 bucket（10%）
if [ "$PERCENT" -gt 0 ] && [ "$GRAY_BUCKET_COUNT" -eq 0 ]; then
    GRAY_BUCKET_COUNT=1
fi

# -----------------------------
# 写入新版 gray.conf
# -----------------------------
cat > $NGINX_GRAY_CONF <<EOF
# 本文件由 gray.sh 自动生成
map \$request_id \$gray_bucket {
    "~(?<num>[0-9])$" \$num;
}

map \$gray_bucket \$version {
EOF

for i in $(seq 0 9); do
    if [ "$i" -lt "$GRAY_BUCKET_COUNT" ]; then
        echo "    $i  v2;" >> $NGINX_GRAY_CONF
    else
        echo "    $i  v1;" >> $NGINX_GRAY_CONF
    fi
done

echo "}" >> $NGINX_GRAY_CONF

# -----------------------------
# 重载 Nginx
# -----------------------------
nginx -t
if [ $? -ne 0 ]; then
    echo "❌ Nginx 配置错误，正在回滚..."
    cp $BACKUP $NGINX_GRAY_CONF
    exit 1
fi

nginx -s reload
echo "✅ 灰度比例已更新为 ${PERCENT}%"
```

## 🔵 Grayscale failure → Automatically downgrade to stable version {#🔵-灰度失败-→-自动降级到稳定版本}

**The "grayscale failure → automatic downgrade to stable version" mechanism that can be used in production**, including:

- ✔ The front-end automatically detects the grayscale version and fails to load it.
- ✔ Automatically reload stable version (v1)
- ✔ Avoid infinite loops + ensure that users can finally access normally
- ✔ Works with Vue CLI / Vite / SPA
- ✔ Can be used with Nginx grayscale publishing at the same time



#### 🟦 1. Core idea {#🟦-一、核心思路}

Problems that Grayscale (v2) users may encounter:

* New version of JS failed to load (network/CDN/packaging error)
* White screen (entry file load failed)
* Static resources 404
* Some file cache conflicts

**When v2 fails, it should be automatically downgraded to v1 to ensure that users are not affected.**

The mechanism is as follows:

1. The browser loads grayscale index.html (pointing to v2/main.js)
2. If any entry file (main.js/chunk) fails to load
3. Automatically switch cookies: `version=v1`
4. **Force Refresh** Load the page of the old version v1
5. Never get stuck in a loop: try at most 1 time


#### 🟦 2. Nginx diversion (prerequisite) {#🟦-二、nginx-分流-前提}

Nginx diverts traffic based on cookies:

```nginx
map $http_cookie $version {
    "~*version=v2"  v2;
    default         v1;
}
```

Grayscale users have `version=v2` → load v2
Downgrade users `version=v1` → stable version v1


#### 🟦 3. Front-end automatic downgrade script (placed at the top of index.html) {#🟦-三、前端自动降级脚本-放在-index-html-顶部}

**This is the key!**
To be placed in `<head>` of `index.html`, prior to all JS loading.

```html
<script>
(function () {
  // 降级标记（防无限循环）
  const retryKey = 'gray_retry';

  // 若已经降级过一次，不再重复
  if (localStorage.getItem(retryKey) === 'done') return;

  // 全局资源加载失败监听
  window.addEventListener('error', function (e) {
    const target = e.target;

    // 仅处理 JS/CSS 资源错误
    if (target.tagName === 'SCRIPT' || target.tagName === 'LINK') {
      // 记录已降级
      localStorage.setItem(retryKey, 'done');

      // 切换到稳定版 v1
      document.cookie = "version=v1; path=/; max-age=3600";

      // 刷新页面重新加载 v1 资源
      window.location.reload(true);
    }
  }, true);
})();
</script>
```


#### 🟦 4. How downgrade works {#🟦-四、降级的工作原理}

Assuming grayscale user loads:

```
/v2/js/main.abc123.js
```

if:

* Corrupted file
* CDN deployment is incomplete
* JS error reporting
* 404
* Chunk lost (lazy loading failed)

The browser triggers the `window.error` event (resource loading exception).

Then the script will automatically:

###### 1. Set downgrade flag to avoid infinite reload {#_1-设置降级标记-避免无限-reload}

```js
localStorage.setItem('gray_retry', 'done');
```

###### 2. Switch cookies {#_2-切换-cookie}

```js
document.cookie = "version=v1; path=/";
```

###### 3. Refresh the page now → load stable version v1 {#_3-立即刷新页面-→-加载稳定版本-v1}

```js
window.location.reload(true);
```


#### 🟦 5. Make sure there is no infinite loop (prevent infinite loop) {#🟦-五、确保不会无限循环-防止死循环}

Only one downgrade is allowed to be triggered:

```js
if (localStorage.getItem(retryKey) === 'done') return;
```

So the logic is:

* The first grayscale loading fails → automatic downgrade
* The second loading (stable version v1) will definitely not fail → will not be triggered repeatedly


#### 🟦 6. Additional enhancement: Capture JS Runtime white screen error {#🟦-六、额外增强-捕获-js-runtime-白屏错误}

Sometimes it's not the resource that fails, but the code runtime that crashes (Vue initialization fails).

plus:

```html
<script>
window.addEventListener("error", function(e) {
  // runtime 错误白屏（灰度版本常见）
  if (e.message && localStorage.getItem("gray_retry") !== "done") {
    localStorage.setItem("gray_retry", "done");
    document.cookie = "version=v1; path=/;";
    location.reload();
  }
});
</script>
```


#### 🟦 7. Additional enhancement: Capture uncaught Promise errors {#🟦-七、额外增强-捕获未捕获-promise-错误}

Many chunk loading failures will go here:

```html
<script>
window.addEventListener("unhandledrejection", function(e) {
  if (localStorage.getItem("gray_retry") === "done") return;

  // 如果是动态 chunk 加载失败
  if (e.reason && e.reason.message && e.reason.message.includes('Loading chunk')) {
    localStorage.setItem("gray_retry", "done");
    document.cookie = "version=v1; path=/;";
    location.reload();
  }
});
</script>
```

You now have a complete "automatic downgrade on grayscale failure" mechanism:

- ✔ Automatically detect entry JS/chunk failure
- ✔ Automatically downgrade to stable version
- ✔Auto refresh
- ✔ Will not trigger repeatedly (avoid infinite loop)
- ✔ Can be combined with Nginx grayscale strategy
- ✔ SPA (Vue) natural support

Final effect:

This is a necessary mechanism for large-scale grayscale releases by enterprises.
