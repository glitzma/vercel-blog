## Static asset canary releases {#🔵-静态资源灰度发布-canary-release-for-static-assets}

Serve new HTML to a cohort while other users receive the old version. The key is **stable assignment, fixed asset versions, retained artifacts and rollback**. This example uses Nginx, a persistent cohort cookie and versioned directories.

## Nginx / CDN assignment {#⭐-方案-1-nginx-cdn-分流-最常用、最稳定}

<span id="⛳-思路"></span>
<span id="🔧-nginx-配置示例-按-cookie-分流"></span>
<span id="用法"></span>
<span id="优点"></span>


Assign at the HTML entry with a stable user identifier or a first-visit cookie, rather than rerandomizing each request. Versioned asset URLs keep open pages on their corresponding artifacts.

## CDN edge assignment {#⭐-方案-2-cdn-边缘规则灰度-企业常用-如阿里云、cloudflare}

<span id="示例-cloudflare-worker-php-rule"></span>


CDN rules or edge functions can implement this logic if supported. Bypass shared HTML caching or partition it by version, rather than serving one user’s entry to everyone. Share assets by versioned URL.

## HTML entry selection {#⭐-方案-3-html-层-ab-test-适用于-spa}

<span id="⛳-思路-1"></span>


HTML references `/releases/v1/js/app.hash.js` or `/releases/v2/js/app.hash.js`. Dynamic imports and CSS image/font URLs must follow the same base/publicPath.

## Application-level switching {#⭐-方案-4-单页应用内部版本切换-有限场景}

Loading another module version internally requires state, shared dependencies and initialization handling. Full SPAs usually select at the HTML entry; server rollback does not switch running pages automatically.

## `CI/CD` rollout {#⭐-方案-5-ci-cd-流程灰度}

Deploy complete artifacts before opening a small cohort, then increase traffic based on observations. Rollback changes new entry selection while retaining assets for open pages.

## Vue deployment example {#🔵-vue-项目静态资源灰度发布-完整可落地案例}

<span id="📌-场景"></span>


This build targets Vue CLI; Vite uses the corresponding base setting. v1/v2 are illustrative: use immutable release identifiers and never overwrite long-cached assets.[publicPath](https://cli.vuejs.org/config/#publicpath).

### 1. Build versioned artifacts {#第一步-构建产物做版本隔离}

<span id="🔧-build-脚本-package-json-加-version-参数"></span>


`vue.config.js`:

```js
const version = process.env.APP_VERSION || 'v1';
if (!/^v[0-9]+$/.test(version)) throw new Error('Invalid release version');
module.exports = {
  publicPath: '/releases/' + version + '/',
  outputDir: 'dist/' + version
};
```

```bash
APP_VERSION=v1 npx vue-cli-service build
APP_VERSION=v2 npx vue-cli-service build
```

### 2. Server layout {#第二步-服务器结构}

```text
/var/www/my-app/releases/
  v1/index.html
  v1/js/app.<hash>.js
  v1/css/app.<hash>.css
  v2/index.html
  v2/js/app.<hash>.js
  v2/css/app.<hash>.css
```

### 3. Nginx routing {#第三步-nginx-灰度配置-核心}

<span id="🔧-nginx-配置-可直接复制"></span>
<span id="✔-说明"></span>
<span id="第四步-给灰度用户注入-cookie"></span>


Place this in the http context; port 8080 is for local verification. Use the real domain and HTTPS in production, adding Secure to cookies. Cohort cookies are not authorization credentials.

```nginx
map $cookie_gray_id $gray_seed {
    "~^[0-9a-f]{32}$" $cookie_gray_id;
    default $request_id;
}
map $cookie_gray_id $gray_seed_cookie {
    "~^[0-9a-f]{32}$" "";
    default "gray_id=$gray_seed; Path=/; Max-Age=2592000; HttpOnly; SameSite=Lax";
}
# Included exactly once in the http context.
include /etc/nginx/gray-split.conf;
map $cookie_version $version {
    v1 v1;
    default $gray_candidate;
}
server {
    listen 8080;
    server_name localhost;
    location ~ ^/releases/v[0-9]+/index\.html$ {
        root /var/www/my-app;
        try_files $uri =404;
        add_header Cache-Control "no-store" always;
    }
    location /releases/ {
        root /var/www/my-app;
        try_files $uri =404;
        add_header Cache-Control "public, max-age=31536000, immutable";
    }
    # SPA entry only; real applications need separate API/proxy locations.
    location / {
        root /var/www/my-app/releases/$version;
        try_files /index.html =404;
        add_header Cache-Control "no-store" always;
        add_header Set-Cookie $gray_seed_cookie always;
    }
}
```

Initial `/etc/nginx/gray-split.conf`:

```nginx
split_clients "$gray_seed:release-v2" $gray_candidate {
    10% v2;
    *   v1;
}
```

split_clients hashes the whole stable identifier and covers every input instead of taking a hexadecimal request_id digit. First-visit HTML sets gray_id for reuse. Percentages partition hash space; user counts vary statistically. Disabled cookies or simultaneous first requests may change assignment, while assets remain versioned.[split_clients](https://nginx.org/en/docs/http/ngx_http_split_clients_module.html).

### 4. Rollback {#第五步-回滚方案-非常重要}

<span id="❌-发现问题-一键回滚"></span>
<span id="第六步-ci-cd-自动化-可选"></span>
<span id="🟢-最终效果"></span>


Map every input to v1, run `nginx -t` and reload. Open v2 pages and lazy imports may still need v2; retain its directory for page sessions, caches and Service Worker use.

```nginx
split_clients "$gray_seed:release-v2" $gray_candidate {
    * v1;
}
```

## Rollout percentage script {#🔵-灰度自动化脚本}

<span id="🟦-1-nginx-分流方案-基于随机数灰度"></span>
<span id="🟦-2-灰度脚本-gray-sh-支持-0–100-任意比例"></span>
<span id="🟦-3-使用方式-非常简单"></span>
<span id="✔-灰度-10"></span>
<span id="✔-灰度提升到-30"></span>
<span id="✔-灰度-90"></span>
<span id="✔-全量-100"></span>
<span id="✔-关闭灰度-回滚-v1"></span>
<span id="🟦-4-日志查看-确认灰度比例"></span>
<span id="🟦-5-在-ci-cd中使用"></span>
<span id="🟢-最终效果-你已经具备"></span>


Accept integers 0–100 with explicit endpoint branches. The file must already exist, and the runner needs write and Nginx permissions. Serialize concurrent rollout jobs in CI.

```bash
#!/usr/bin/env bash
set -euo pipefail

percent=${1:-}
if [[ ! "$percent" =~ ^(0|[1-9][0-9]?|100)$ ]]; then
  echo "Usage: gray.sh <integer 0-100>" >&2
  exit 1
fi
conf=/etc/nginx/gray-split.conf
backup=$(mktemp)
pending=$(mktemp /etc/nginx/gray-split.conf.XXXXXX)
trap 'rm -f "$backup" "$pending"' EXIT
cp "$conf" "$backup"
{
  echo 'split_clients "$gray_seed:release-v2" $gray_candidate {'
  if (( percent == 0 )); then
    echo '    * v1;'
  elif (( percent == 100 )); then
    echo '    * v2;'
  else
    echo "    $percent% v2;"
    echo '    * v1;'
  fi
  echo '}'
} > "$pending"
# Keep the existing file permissions.
cat "$pending" > "$conf"
if ! nginx -t; then
  cat "$backup" > "$conf"
  echo "Invalid configuration; restored previous file" >&2
  exit 1
fi
if ! nginx -s reload; then
  cat "$backup" > "$conf"
  nginx -s reload || true
  echo "Reload failed; restored previous file" >&2
  exit 1
fi
echo "Configured canary hash-space share: $percent%"
```

```bash
bash gray.sh 15
bash gray.sh 100
bash gray.sh 0
```

These configure 15%, full rollout and rollback. Recovery cookies temporarily retain v1 outside normal assignment. Use observations to decide traffic increases.

## Recovery from failed canary resources {#🔵-灰度失败-→-自动降级到稳定版本}

<span id="🟦-一、核心思路"></span>
<span id="🟦-二、nginx-分流-前提"></span>
<span id="🟦-三、前端自动降级脚本-放在-index-html-顶部"></span>
<span id="🟦-四、降级的工作原理"></span>
<span id="_1-设置降级标记-避免无限-reload"></span>
<span id="_2-切换-cookie"></span>
<span id="_3-立即刷新页面-→-加载稳定版本-v1"></span>
<span id="🟦-五、确保不会无限循环-防止死循环"></span>
<span id="🟦-六、额外增强-捕获-js-runtime-白屏错误"></span>
<span id="🟦-七、额外增强-捕获未捕获-promise-错误"></span>
<span id="🟢-最终你拥有的能力"></span>


Place this before entry resources in both HTML versions. It handles script/link failures only for the specified version, cannot eliminate every white screen and should not treat every business error as a rollback reason.

```html
<script>
(function () {
  const failedVersion = 'v2';
  const retryKey = 'gray_retry:' + failedVersion;
  window.addEventListener('error', function (event) {
    const target = event.target;
    if (!target || !['SCRIPT', 'LINK'].includes(target.tagName)) return;
    const resource = target.src || target.href;
    if (!resource) return;
    const url = new URL(resource, location.href);
    if (url.origin !== location.origin ||
        !url.pathname.startsWith('/releases/' + failedVersion + '/')) return;
    try {
      if (sessionStorage.getItem(retryKey)) return;
      sessionStorage.setItem(retryKey, 'done');
    } catch {
      return; // Storage unavailable: avoid uncontrolled reload loops.
    }
    document.cookie = 'version=v1; Path=/; Max-Age=3600; SameSite=Lax';
    location.reload();
  }, true);
})();
</script>
```

Catch dynamic-import failures at the call site and decide initialization recovery using framework hooks and business state. Stable releases can also fail, so retain an error view and diagnostic path. Update version and retry keys each release.

## Verification and cache requirements {#🔥-关键注意点}

<span id="_1-必须使用带-hash-的构建产物"></span>
<span id="_2-旧版本资源必须继续保留"></span>
<span id="_3-index-html-才是灰度的关键"></span>
<span id="🟢-给你一个非常简短易记的总结"></span>


1. Check that entries, dynamic chunks and CSS image/font URLs contain the version.
2. Repeated HTML requests with one gray_id should remain stable; test 0%, 15%, 100% without exact small-sample ratios.
3. Test known assets under `/releases/v1/` and `/releases/v2/`, cache headers and missing-asset 404s.
4. Return HTML for SPA deep links, route APIs separately, avoid shared cohort HTML caching and stale Service Worker entries.
5. Simulate a v2 entry failure, allow at most one recovery attempt and retain assets for open pages after rollback.
