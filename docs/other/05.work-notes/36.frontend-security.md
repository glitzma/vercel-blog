## 1\. What does front-end security protect against? {#一、前端安全到底在防什么}

There is only one core goal:

> **Prevent user-controllable data from being executed as "code"**

The nature of the attack is usually:

* Injection
* Override (Auth/Permissions)
* information leakage
* supply chain attack


## 2\. Must-test and must-understand front-end security issues {#二、必考-必会的前端安全问题}

### 1️⃣ XSS (cross-site scripting attack) ⭐⭐⭐⭐⭐ {#_1️⃣-xss-跨站脚本攻击-⭐⭐⭐⭐⭐}

#### essence {#本质}

> User input → executed by the browser as JS

#### Type {#类型}

| Type | Description |
| ----- | ------------ |
| Storage type | Malicious scripts stored in database |
| Reflective | URL parameters are executed directly |
| DOM type | JS operating DOM results in |

#### Example {#示例}

```html
<div id="app"></div>
<script>
  const name = location.search.slice(6)
  document.getElementById('app').innerHTML = name
</script>
```

Visit:

```
?name=<img src=x onerror=alert(1)>
```


#### Defense Plan (Key Points) {#防御方案-重点}

✅ **Never trust user input**

1️⃣ Output encoding (most important)

```js
element.textContent = userInput
```

2️⃣ Avoid `innerHTML / v-html / dangerouslySetInnerHTML`

3️⃣ Rich text → **Whitelist filtering**

* DOMPurify
* sanitize-html

4️⃣ CSP (Content Security Policy)

```http
Content-Security-Policy:
  default-src 'self';
  script-src 'self';
```

5️⃣ Cookie settings

```http
Set-Cookie: token=xxx; HttpOnly; Secure
```


### 2️⃣ CSRF (Cross-site request forgery) ⭐⭐⭐⭐⭐ {#_2️⃣-csrf-跨站请求伪造-⭐⭐⭐⭐⭐}

#### essence {#本质-1}

> Use your browser to automatically carry cookies

#### Example {#示例-1}

```html
<img src="https://bank.com/transfer?to=hacker&money=10000">
```


#### defense plan {#防御方案}

1️⃣ CSRF Token (mainstream)

```js
headers: {
  'X-CSRF-TOKEN': token
}
```

2️⃣ SameSite Cookie

```http
Set-Cookie: session=xxx; SameSite=Lax
```

3️⃣ Verify Referer / Origin


### 3️⃣ Clickjacking {#_3️⃣-点击劫持-clickjacking}

#### essence {#本质-2}

> iframe transparent coverage to induce clicks

#### defense {#防御}

```http
X-Frame-Options: DENY
```

or

```http
Content-Security-Policy: frame-ancestors 'none';
```


### 4️⃣ Front-end authentication & unauthorized access issues ⭐⭐⭐⭐ {#_4️⃣-前端鉴权-越权问题-⭐⭐⭐⭐}

#### Common mistakes {#常见错误}

```js
if (user.role === 'admin') {
  showAdminButton()
}
```

⚠️ **Front-end judgment ≠ Security**

#### correct principle {#正确原则}

* Frontend: **Display Control**
* Backend: **Permission verification**


### 5️⃣ Token / JWT Security ⭐⭐⭐⭐ {#_5️⃣-token-jwt-安全-⭐⭐⭐⭐}

#### Common risks {#常见风险}

* Save localStorage → Easy to XSS theft
* JWT never expires

#### Recommended plan {#推荐方案}

| Scenario | Suggestions |
| ------------- | --------------- |
| Login status | HttpOnly Cookie |
| Access Token | Short term |
| Refresh Token | HttpOnly        |


### 6️⃣ What can front-end encryption prevent?⭐⭐⭐ {#_6️⃣-前端加密能防什么-⭐⭐⭐}

❌ Cannot stop someone who controls the endpoint from:

* Debugging and reading plaintext at runtime
* Intercepting data at encryption and decryption boundaries
* Reverse engineering and extracting keys embedded in the frontend

✅ With correct algorithms and key management, can protect:

* Data confidentiality, reducing direct plaintext exposure
* Data in transit through HTTPS encryption, integrity protection, and authentication

Common:

* HTTPS
* AES / RSA are cryptographic algorithms, not obfuscation; security depends on modes, parameters, and key management. Keys embedded in the frontend cannot be kept secret from someone who controls that endpoint. [Web Crypto](https://developer.mozilla.org/en-US/docs/Web/API/SubtleCrypto/encrypt).


### 7️⃣ Supply chain security (new focus of modern front-end) ⭐⭐⭐⭐ {#_7️⃣-供应链安全-现代前端新重点-⭐⭐⭐⭐}

#### risk {#风险}

* npm package is poisoned
* Dependency version drift

#### defense {#防御-1}

* `package-lock.json / pnpm-lock.yaml`
* `npm audit`
* fixed version
* Private npm repository


## 3\. Framework layer security (Vue/React) {#三、框架层安全-vue-react}

### Vue

* Default `{{}} ` is automatically escaped
* `v-html` = **High Risk**
* Command parameter injection (`:href="userInput"`)

### React

* JSX safe by default
* `dangerouslySetInnerHTML` = **Dangerous**
* Event binding is safe (strings will not be executed)


## 4\. Safety Checklist in real projects ✅ {#四、真实项目中的安全-checklist-✅}

- ✔ Don’t use `eval / new Function`
- ✔ All APIs use HTTPS
- ✔ Do not store Token in localStorage (or strictly prevent XSS)
- ✔ Secondary confirmation of important operations
- ✔ All interface backends perform authentication
- ✔ Rich text must be sanitized
- ✔ CSP + HttpOnly Cookie


## 5\. Frequently asked questions in interviews (you will definitely encounter them) {#五、面试高频问法-你一定会遇到}

- ❓ What is the difference between XSS and CSRF?

**Standard answer template:**

- XSS injects malicious scripts into the page and attacks the user;
- CSRF uses the user login state to initiate illegal requests and attacks the server.


- ❓ Why can’t the front end perform security verification?

**One sentence:**

- The front-end code is completely tamperable and can only be used as an experience optimization and cannot be used as a security boundary.
