## 1\. What is micro frontend {#一、什么是微前端}

:::tip
Techniques, strategies and recipes for building a modern web app with multiple teams that can ship features independently. -- Micro Frontends

Micro front-end is a technical means and method strategy for multiple teams to jointly build modern web applications by publishing functions independently.
:::

The micro front-end architecture has the following core values:

- Technology stack independent

  The main framework does not limit the technology stack of the access application, and micro-applications have complete autonomy.

- Independent development and independent deployment

  The micro-application warehouse is independent, and the front and back ends can be developed independently. After the deployment is completed, the main framework automatically completes synchronous updates.

- Incremental upgrade

  When faced with various complex scenarios, it is usually difficult for us to fully upgrade or reconstruct the technology stack of an existing system, and micro-frontends are a very good means and strategy for implementing progressive reconstruction.

- standalone runtime
  
  The state of each micro application is isolated and the runtime state is not shared.

The micro-front-end architecture aims to solve the problem of unmaintainability of a single application after it evolves from an ordinary application to a frontend monolith over a relatively long time span due to the increase and changes in the number of people and teams involved.This type of problem is especially common in enterprise web applications.

### 2\. Comparison of architectural principles (brief description) {#二、架构原理对比-简述}

| Framework | Isolation mechanism | Communication mechanism | Loading method |
| ------------- | ---------------------------------------------------- | ------------------------ | --------------------- |
| **Qiankun** | JS: Proxy sandbox<br>CSS: manual scope or BEM | props + globalState | HTML entry pull |
| **micro-app** | JS: Proxy sandbox + iframe isolation options<br>CSS: Shadow DOM + scoped | window.microApp.dispatch | script + WebComponent |
| **Wujie** | Complete iframe-level isolation<br>Communication: postMessage + Bridge | Master communicates through wujie.bus | iframe lazy loading + preloading |



| Framework | Implementation mechanism | Description |
| ------------- | --------------------------------- | ------------------------------------------------ |
| **iframe** | Browser native isolation | Each sub-application runs in an independent window context, naturally isolating DOM, JS, and CSS |
| **qiankun** | Based on **single-spa + JS sandbox** | The sub-application HTML parsing and JS execution are in the Proxy environment, and the sandbox is implemented by hijacking `window` |
| **micro-app** | **CustomElement + Proxy Sandbox** | The sub-application is mounted as a custom element (`<micro-app>`) and uses ShadowDOM + sandbox to achieve isolation |
| **EMP** | **Webpack Module Federation** | Expose modules at build time and dynamically load them at runtime (not true runtime isolation) |
| **Unbounded (wujie)** | **iframe + main-app DOM reuse + sandbox** | The sub-application runs in the document of the iframe, but shares the routing and context of the main application |


### 3\. Summary of actual experience {#三、实际体验总结}

#### ✅ 1. Qiankun (the most mature) {#✅-1-qiankun-最成熟}

* Advantages:

  * The fastest to get started and the documentation is complete.
  * The ecosystem is mature and there are many answers to community questions.
  * Seamlessly integrates with Vue and React projects.
* Disadvantages:

  * The performance is not optimal, and switching sub-applications is expensive.
  * Sandbox isolation has boundaries, and some global dependencies are prone to conflicts.
* **Recommendation**: Suitable for existing system modifications or teams that need to quickly build a micro front-end framework.
* Applicable scenarios: Large-scale B-side systems, compatible with Vue2/React old project transformation


#### ✅ 2. micro-app (both performance and isolation) {#✅-2-micro-app-性能与隔离兼顾}

* Advantages:

  * Native WebComponent mechanism, good isolation and fast loading.
  * Supports keep-alive, preloading, iframe mixing and other optimizations.
  * Integrate with any framework (even plain HTML).
* Disadvantages:

  * Some advanced feature documentation is not detailed.
  * Sandbox compatibility is slightly worse than qiankun.
* **Recommendation**: Suitable for new systems, cross-framework scenarios (React+Vue coexistence), and performance-sensitive projects.
* Applicable scenarios: New projects that pursue performance, have high compatibility requirements, and want to be framework-independent


#### ✅ 3. Wujie (the most complete isolation) {#✅-3-wujie-隔离最彻底}

* Advantages:

  * iframe is truly isolated, no need to worry about style or script conflicts.
  * The communication mechanism is flexible and secure.
  * Supports the coexistence of multiple instances.
* Disadvantages:

  * iframe loading is slightly slow, affecting the first screen.
  * It is difficult to share resources between sub-applications.
  * The development experience is complicated.
* **Recommendation**: Suitable for projects with high security requirements (such as banking, government affairs, intranet).
* Applicable scenarios: high security scenarios (such as financial systems), independent delivery by multiple teams, extremely high isolation requirements


### 4\. Selection of suggestions (by project type) {#四、选择建议-按项目类型}

| Project Type | Recommended Framework | Rationale |
| ------------------------ | ------------- | ----------- |
| Micro front-end transformation of old projects (Vue2/React) | **Qiankun** | Stable and easy to migrate |
| New project + pursuit of performance | **micro-app** | Fast loading + good isolation |
| Finance/Government Affairs + High Security | **Wujie** | True isolation, pollution prevention |
| Multi-framework coexistence (Vue, React, Angular) | **micro-app** | Strong framework independence |


### 5\. Summary (short version) {#五、总结-简短版}

> * **Qiankun**: Based on single-spa, the ecology is mature and suitable for the transformation of old systems, but the isolation is average.
> * **micro-app**: Using WebComponent technology, it has better performance and stronger isolation, suitable for new projects.
> * **Wujie**: Use iframe to achieve complete isolation, with the highest security, suitable for high security scenarios.
>   When making the actual choice, I will make a comprehensive judgment based on performance, security, and team framework compatibility.


## 2\. Routing {#二、路由}

The virtual routing system is consistent with the routing behavior of the browser. It rewrites popState and hashChange events by customizing core routing APIs such as location and history, intercepts routing navigation and events, and provides a series of custom APIs to simulate routing behaviors such as rendering, jumping and returning of web applications in a browser environment.Sub-applications run in this virtual routing system and are isolated from the base application's routing, thereby avoiding mutual influence and enhancing the ability to interact between sub-applications and the base application.Through the virtual routing system, the base application can easily obtain the routing information of the sub-application and control the jump of the sub-application. The routing information of the sub-application will be synchronized to the browser address as a parameter.In addition, the virtual routing system also provides many functions to help developers improve work efficiency.
| Framework | Implementation | Features |
| ------------- | ----------------------------- | ------------------------------------------------- |
| **iframe** | Independent routing system | Each iframe has its own URL, not shared with the main application |
| **qiankun** | Route hijacking (`popstate`, `hashchange`) | The main application uniformly controls routing and loads sub-applications through activeRule matching |
| **micro-app** | Independent routing + synchronization mechanism | The sub-application runs in ShadowDOM and uses `micro-app-router` to synchronize with the main router |
| **EMP** | Routing is controlled by the host | After the module is imported, it is mounted to the specified routing component, usually relying on the host React/Vue Router |
| **Unbounded (wujie)** | Routing synchronization within iframe | The main and child application routing synchronization mechanism is strong, and the `sync` attribute can be used to control the routing strategy |

✅ Summary of routing mechanism:

* qiankun and micro-app are dynamically loaded at runtime;

* EMP is shared during construction;

* Unbounded hybrid model combines flexibility and isolation.

## 3\. web components {#三、web-components}

Can be used to build large component libraries, such as UI component libraries.Components such as buttons, forms, menus, etc. can be developed as Web Components.Such component libraries can be reused by different projects to improve development efficiency.For example, a company can develop an internal UI component library that contains a variety of components with a unified style for use by various product teams.

In the micro front-end architecture, each micro application can be encapsulated into a Web Component.Different teams can develop their own microapps independently and then combine them into a complete application.For example, an e-commerce website can have product display micro-applications, shopping cart micro-applications, user login micro-applications, etc. These micro-applications can be integrated through Web Components.

| ------------- | ----------------------------- | ---------------------- |
| **iframe** | Browser native isolation | ⭐⭐⭐⭐ (the most thorough) |
| **qiankun** | `ScopedCSS` + `ShadowDOM` (optional) | ⭐⭐ (partially isolated) |

## 5\. How to communicate {#五、如何通讯}

- Data transmission is based on URL, but the ability to transmit messages is weak
- Implement communication based on customEvent
- Communication between main and subcomponents based on props
- Use global variables and Redux for communication

| Framework | Communication Methods | Description |
| ------------- | -------------------------- | --------------- |
| **iframe** | `postMessage` | Native API, but coding is troublesome and asynchronous |
| **qiankun** | `initGlobalState()` Global shared state | Similar to Redux, can monitor changes |
| **micro-app** | `data` attribute + custom event + global communication | Supports two-way binding style, simple and easy to use |
| **EMP** | Directly import shared modules | Share dependencies during construction and synchronize data in real time |
| **Unbounded (wujie)** | `bus` communication mechanism | Master and child applications share a communication bus |

* ✅ micro-app / Unbounded → Simple and responsive communication;
* ✅ EMP → Optimal within the engineering system (no runtime communication required).

#### qiankun plan {#qiankun方案}

##### 🧩 1. What is qiankun? {#🧩-一、qiankun-是什么}

> **qiankun is a micro front-end framework implemented based on single-spa**,
> The core idea is to allow multiple independently running front-end applications (different technology stacks) to coexist smoothly in the same main application.

Its core goals:

* Sub-applications are independently developed, constructed, and deployed independently;
* The main application loads, registers and communicates in a unified manner;
* Technology stack independent (Vue, React, Angular are all acceptable).


##### ⚙️ 2. The core principles of qiankun {#⚙️-二、qiankun-的核心原理}

| Module | Implementation ideas |
| ------------- | --------------------------------------- |
| **Runtime Scheduling** | Based on single-spa, hijack routing and load sub-applications according to activation rules |
| **Resource Loading** | Intercept sub-application HTML and parse out JS/CSS dynamic injection (supports preloading) |
| **JS Isolation (Sandbox)** | Isolate sub-application global variables through Proxy + Snapshot sandbox |
| **Style Isolation** | ShadowDOM (experimental) or scoped CSS prefix for style scope control |
| **Communication Mechanism** | Provides `initGlobalState` to achieve data synchronization between master and child applications |
| **Life cycle management** | Provides `bootstrap`, `mount`, `unmount` life cycle hooks |
| **Routing mechanism** | Sub-application independent routing system, which can be synchronized with the main application hash/history |


##### 🧠 3. Advantages (advantages) of qiankun {#🧠-三、qiankun-的优点-优势}

| Advantages | Description |
| ------------------ | ----------------------------------------------- |
| ✅ **1. Mature and stable, huge community** | Maintained by the Alibaba team, the ecosystem is the most complete, the documentation is detailed, and it is widely used (used by Alibaba Cloud, DingTalk, Cainiao, etc.).|
| ✅ **2. Supports multiple technology stacks** | The master and child applications can use different frameworks such as Vue, React, and Angular respectively without affecting each other.|
| ✅ **3. Simple access and low intrusion** | Sub-applications hardly need to modify the business code and only need to expose life cycle hooks.|
| ✅ **4. Improved isolation mechanism** | Supports JS sandbox (Proxy + Snapshot) and CSS isolation to prevent style and global variable conflicts.|
| ✅ **5. Complete life cycle** | Provides bootstrap, mount, and unmount life cycles to finely control loading and unloading behavior.|
| ✅ **6. Support resource preloading** | Sub-applications can load resources in advance before being activated to improve switching performance.|
| ✅ **7. Clear data communication mechanism** | Official `initGlobalState` supports master-child and child-child application communication.|
| ✅ **8. Strong scalability** | Supports manual loading of sub-applications, customized loading strategies, preloading strategies, error boundaries, etc.|


##### ⚠️ 4. Disadvantages (limitations) of qiankun {#⚠️-四、qiankun-的缺点-局限性}

| Disadvantages | Description |
| -------------------- | --------------------------------------------- |
| ❌ **1. Poor startup performance** | Each sub-application needs to parse, load, and execute HTML, CSS, and JS independently, and the first screen loads slowly.|
| ❌ **2. JS sandbox performance overhead is high** | Proxy/Snapshot sandbox has obvious performance loss during frequent mount/unmount.|
| ❌ **3. Incomplete style isolation** | scopedCSS has limited isolation effect on the global styles of third-party libraries (such as ElementUI).|
| ❌ **4. Difficulty sharing dependencies between multiple applications** | Sub-applications are packaged separately, causing React/Vue, etc. to be loaded repeatedly and occupy space.|
| ❌ **5. Complicated debugging** | Dynamic loading of sub-application resources makes SourceMap positioning difficult.|
| ❌ **6. Cross-domain issues require manual configuration** | When sub-applications are deployed to different domain names, CORS or proxy needs to be set up.|
| ❌ **7. Poor SSR support** | qiankun is mainly oriented to SPA architecture, and SSR support is almost zero.|
| ❌ **8. Limited integration with modern build tools** | Weak support for Vite and ESM build ecology, relying on the Webpack build system.|

##### 🧭 6. Suggestions for applicable scenarios {#🧭-六、适用场景建议}

✅ **Recommended circumstances for using qiankun:**

* Medium and large-scale platforms developed in parallel by multiple teams;
* Master and child applications use different frameworks;
* A stable, mature, and well-established community solution is needed;

⚠️ **Case in which qiankun is not recommended:**

#### micro-app solution {#micro-app-方案}

##### 🧩 1. What is micro-app? {#🧩-一、micro-app-是什么}

> **micro-app is a micro front-end framework based on the Web Components specification.**
>
> It implements "componentized micro frontend" by creating a custom tag `<micro-app>` to load sub-applications.

Example:

```html
<micro-app name="sub-vue" url="http://localhost:8080/"></micro-app>
```

Features:

* Use custom elements to wrap sub-applications;
* Sub-applications run in a virtual sandbox;
* Supports the isolation of styles, JS, and DOM;
* Master-child application communication is simple;
* No iframe required and no reliance on build-time federation.


##### ⚙️ 2. Core implementation principles of micro-app {#⚙️-二、micro-app-的核心实现原理}

| Module | Principle Description |
| ------------------- | ------------------------------------- |
| **WebComponent packaging** | Each sub-application is wrapped in a custom tag `<micro-app>` |
| **JS Sandbox** | Implement JS isolation environment through Proxy + iframe window simulation |
| **Style Isolation** | Use Shadow DOM + scoped style prefix to achieve CSS isolation |
| **DOM Isolation** | Each sub-application has an independent virtual DOM tree, isolated from the main application |
| **Resource Loading** | Intercept sub-application HTML, JS, CSS requests, rewrite the path and dynamically inject |
| **Communication mechanism** | Realize master-slave communication based on global events and data bus (eventCenter) |
| **Routing mode** | Supports independent routing and master-child synchronization (hash/history) |


##### 🧠 3. Advantages (advantages) of micro-app {#🧠-三、micro-app-的优点-优势}

| Advantages | Description |
| --------------------------- | ---------------------------------------------------------------------------------------- |
| ✅ **1. High performance** | - Sub-applications run directly in the main page context, without iframe process switching overhead <br> - Style isolation based on Shadow DOM to avoid global pollution <br> - Reusable cache to achieve "second opening" experience |
| ✅ **2. High compatibility** | - Supports Vue, React, Angular, and mini program web projects <br> - Friendly to old projects, low access cost |
| ✅ **3. Low intrusiveness** | - Sub-applications require almost no modifications <br> - No need to adjust webpack build configurations |
| ✅ **4. Improved sandbox isolation** | - JS achieves independent scope through Proxy <br> - Style isolation through Shadow DOM <br> - DOM mount point is independent and will not pollute the main application |
| ✅ **5. Flexible communication mechanism** | - Built-in global event center (`eventCenter`) <br> - Master and child can communicate in two directions (emit/on) |
| ✅ **6. Strong routing control** | - Sub-applications can use their own routing system <br> - They can also be switched synchronously with the main application routing |
| ✅ **7. Rich life cycle** | - Provides complete life cycle hooks (mount/unmount/hidden/show) <br> - Can implement cache, keep-alive and other functions |
| ✅ **8. Support SSR / KeepAlive** | - Sub-applications can cache DOM and restore quickly <br> - Support SSR loading scenarios (via DOM injection) |


##### ⚠️ 4. Disadvantages (limitations) of micro-app {#⚠️-四、micro-app-的缺点-局限性}

| Disadvantages | Description |
| --------------------------------- | -------------------------------------------------------------------- |
| ❌ **1. Sandbox overhead is high** | - Proxy sandbox simulation window, there is performance loss <br> - CPU overhead is obvious when loading large sub-applications |
| ❌ **2. Not suitable for older browsers** | - Relies on new features such as Web Components, Proxy, Shadow DOM, etc. <br> - Requires a modern browser (Chrome 60+) |
| ❌ **3. High debugging complexity** | - The sub-application runs in a virtual environment, and debugging variables and scopes are not intuitive |
| ❌ **4. Cross-domain issues need to be handled manually** | - Sub-application resources (JS/CSS) need to be configured with CORS or proxy when crossing domains |
| ❌ **5. The initial loading speed is slightly slower** | - The first loading of the sub-application requires dynamic parsing of HTML and injecting scripts <br> - The parsing process is slightly slower than qiankun |
| ❌ **6. SSR support is incomplete** | - Official support is limited and requires customized rendering logic |
| ❌ **7. Sub-applications still need to regulate global styles and window object operations** | - If sub-applications directly modify global styles and register global variables, conflicts may occur |


##### 🔍 5. Comparison with other micro front-end frameworks {#🔍-五、与其他微前端框架对比-1}

| Comparison items | **micro-app** | **qiankun** | **Wujie** | **EMP** |
| ------ | ----------------------- | --------------------- | ------------- | ----------------- |
| Implementation mechanism | WebComponent + Proxy sandbox | single-spa + Proxy sandbox | iframe + sandbox hybrid | Module Federation |
| Isolation | ⭐⭐⭐⭐ | ⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐ |
| Performance | ⭐⭐⭐⭐ | ⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| Architecture granularity | Application level | Application level | Application level | Module level |
| Communication method | eventCenter | initGlobalState | bus | JS call |
| Style isolation | Shadow DOM | scopedCSS | iframe/Scoped | None |
| Routing Support | Strong | Strong | Strong | Weak |
| SSR Support | Fair | Fair | Weak | Weak |
| Compatibility | Modern browsers | Strongest | Moderate | Same stack projects |
| Ecological community | Active | Most mature | Stable | Emerging |


##### 🧭 6. Suggestions for applicable scenarios {#🧭-六、适用场景建议-1}

✅ **Recommended situations for using micro-app:**

* For medium and large front-end platforms, the main and sub-project technology stacks are similar;
* Pursue a good balance of performance and isolation;
* Want low-cost access;
* Caching, instant opening, and flexible communication are required.

⚠️ **Not recommended:**

* Needs compatibility with IE or old browsers;

> **micro-app is the micro front-end framework closest to "front-end native implementation":**

> Suitable for modern browsers, single-page architecture and multi-team parallel development scenarios.


#### EMP scheme {#emp-方案}

##### 🧩 1. What is EMP? {#🧩-一、emp-是什么}

**EMP (Easy Micro Frontend Platform)** is a micro frontend framework based on **Webpack5 Module Federation** package.
It is not a runtime framework (such as qiankun, micro-app), but a **build-time solution**.

Simple understanding:

> It does not isolate through iframe or sandbox, but builds configuration through webpack, allowing multiple independent applications to share modules and dynamically introduce them during the build phase, achieving "real module-level decoupling."


##### ⚙️ 2. Core principles of EMP {#⚙️-二、emp-的核心原理}

| Module | Implementation |
| -------- | ---------------------------------- |
| **Core Mechanism** | `Module Federation` based on Webpack 5 |
| **Shared module** | Multiple sub-applications share common dependencies (such as React/Vue/Element, etc.) |
| **Module Exposure** | Sub-applications expose components/modules through `exposes` |
| **Module loading** | The main application or other sub-applications dynamically introduce these exposed modules through `remotes` |
| **Running mechanism** | Dynamically load remote modules through remoteEntry.js during runtime (lazy loading) |
| **Build Optimization** | Unified packaging and version alignment of common dependencies between multiple projects |
| **Deployment Strategy** | Can be deployed independently, each application publishes remoteEntry.js to CDN |


##### 🧠 3. Advantages (Advantages) of EMP {#🧠-三、emp-的优点-优势}

| Advantages | Description |
| --------------------------------- | --------------------------------------------------------------------------- |
| ✅ **1. Higher performance (build-level sharing)** | - Based on build-time module sharing instead of runtime sandbox <br> - Shared dependency packages between master and sub-applications, reducing repeated packaging and loading <br> - Significantly reducing bundle size and loading time |
| ✅ **2. True module-level reuse** | - Allows switching between projects **Directly import remote modules or components** <br> - Implement "component-level" micro frontend (more granular than qiankun's "subsystem level") |
| ✅ **3. No runtime performance penalty** | - No dependencies on iframes, sandboxes or WebComponents <br> - Runs directly in the same execution context, no context switch costs |
| ✅ **4. Good development experience** | - No need for sub-applications to modify routing, life cycle, etc. <br> - Almost zero intrusion into Vue/React projects |
| ✅ **5. Hot update friendly (HMR support)** | - Support hot module replacement (Hot Module Replacement) <br> - Submodule changes do not require an overall build |
| ✅ **6. Independent deployment + automatic dependency management** | - Each sub-application can still be deployed independently <br> - Publish remote modules through CDN to achieve flexible combination |
| ✅ **7. High cross-team collaboration efficiency** | - Different teams independently develop and share components <br> - The middle platform or component library has strong reusability |
| ✅ **8. Supports multiple frameworks (Vue/React/Angular)** | - EMP provides Vue and React dual-stack templates <br> - Mixed stack projects can reference each other's modules |


##### ⚠️ 4. Disadvantages (limitations) of EMP {#⚠️-四、emp-的缺点-局限性}

| Disadvantages | Description |
| ---------------------- | ----------------------------------------------------------------------- |
| ❌ **1. Strong dependence on Webpack 5** | - Can only run in Webpack5 environment <br> - Poor compatibility with Vite, Rollup and other ecosystems |
| ❌ **2. Sensitive to version consistency** | - Module Federation has strict requirements on dependent versions (such as React17 vs 18)<br> - Inconsistency may lead to runtime conflicts or repeated loading |
| ❌ **3. The dependency chain is complicated when loading for the first time** | - Dynamically loading remote modules requires an additional request for remoteEntry.js <br> - When there are many remote resources, the performance of the first screen may decrease |
| ❌ **4. The deployment/release process is complex** | - The remoteEntry.js address of each application needs to be maintained <br> - CDN update strategy and cache control need to be handled carefully |
| ❌ **5. Weak security and isolation** | - All modules are executed in the same JS context <br> - If submodules pollute global variables, it will affect the entire system |
| ❌ **6. Debugging is more difficult** | - SourceMap positioning is difficult when dynamically loading remote modules <br> - The error stack may mix module paths of multiple projects |
| ❌ **7. Old projects are not supported** | - The integration of old projects such as Vue2 + Webpack4 requires high migration costs |
| ❌ **8. Weak SSR support** | - Module Federation has limited support for Node SSR environment (requires additional processing of remote dependencies) |

##### 🧭 6. Suggestions for applicable scenarios {#🧭-六、适用场景建议-2}

✅ **Recommended scenarios for using EMP:**

* Multiple mid- and back-end projects in the same company and with the same technology stack;
* Need to share business components and modules efficiently;
* Hope to reduce repeated packaging and improve build speed;
* The front-end and back-end deployment system is controllable (CDN/intranet).

⚠️ **Scenarios where EMP is not recommended:**

* Multi-technology stack hybrid (Vue + React);
* Old project (Webpack <5);
* Extremely high security requirements;
* SSR or Node isomorphic project.


##### 💬 7. One sentence summary {#💬-七、一句话总结-2}

> **EMP is a representation of build-time micro frontend**,
> Focusing on "high-performance module sharing" and "component-level micro front-end",
> Suitable for enterprise scenarios with multiple front-end projects and multiple teams sharing components.
> But it is not suitable for systems with cross-stack and high isolation requirements.


#### Unbounded (Wujie) plan {#无界-wujie-方案}

##### 🧩 1. What is Wujie (Unbounded)? {#🧩-一、wujie-无界-是什么}

> **Wujie is a high-performance, low-intrusion micro front-end framework**,
> It combines the security isolation features of `iframe` and the high-performance routing mechanism of `qiankun`.

It uses:

* **iframe container as the basic isolation environment**,
* At the same time, reuse the DOM, JS context and resources of the main application,
* And achieve a balance of performance and compatibility through "**Master-child routing synchronization + sandbox + communication bus**".


##### ⚙️ 2. Wujie’s core implementation principles {#⚙️-二、wujie-的核心实现原理}

| Module | Implementation ideas |
| -------- | ------------------------------------------------- |
| **Rendering Isolation** | Use the document within the iframe as the execution context, but do not reload the browser context (do not open a new process) |
| **Script Execution** | Inject sandbox (Proxy) to isolate window / document access |
| **Style Isolation** | Implement double-layer isolation through ScopedCSS + iframe |
| **Route Management** | Master and child application routing synchronization (can choose independent or synchronized) |
| **Communication mechanism** | Master and child share a global `event-bus`, which can communicate in both directions |
| **Caching mechanism** | Sub-applications can cache the DOM and open it in seconds upon return (can keep-alive) |


##### 🧠 3. Advantages (Advantages) of Wujie {#🧠-三、wujie-的优点-优势}

| Advantages | Specific instructions |
| ------------------------- | ---------------------------------------------------------------------------- |
| ✅ **1. High performance** | - Sub-applications use iframe document but share resources and do not reload <br> - Almost "seconds to start" when switching applications <br> - Support DOM cache and snapshot recovery |
| ✅ **2. Strong compatibility** | - Compatible with multiple stacks such as Vue2/Vue3/React/Angular <br> - Suitable for old project integration (compatible with lower version browsers) |
| ✅ **3. Strong isolation** | - Implement "semi-isolation" based on iframe document: CSS, JS, and DOM are all isolated <br> - But can access host context variables (controlled exposure) |
| ✅ **4. Flexible routing synchronization** | - You can choose "independent routing mode" or "synchronize main application routing" <br> - Support the coexistence of hash/history two methods |
| ✅ **5. Simple communication** | - Built-in global communication bus (bus)<br> - Supports two-way calls, such as `window.$wujie.bus.emit/on` |
| ✅ **6. Support keep-alive caching** | - The DOM state can be cached after the sub-application is loaded for the first time <br> - The cache node is directly rendered when returning without reloading |
| ✅ **7. Less intrusive** | - Sub-applications require almost no modification <br> - No need to change webpack configuration, no need to modify build commands |
| ✅ **8. Higher security** | - Code is executed in an iframe and does not directly pollute the main application environment <br> - Script injection and resource permissions can be controlled |


##### ⚠️ 4. Disadvantages (limitations) of Wujie {#⚠️-四、wujie-的缺点-局限性}

| Disadvantages | Specific instructions |
| -------------------------- | ------------------------------------------- |
| ❌ **1. High implementation complexity** | The internal mechanism is more complicated than qiankun (iframe + sandbox hybrid), and debugging is difficult.|
| ❌ **2. The community ecology is small** | Compared with qiankun and micro-app, it has less community information and plug-in support.|
| ❌ **3. Debug not friendly** | The sub-application runs within an iframe, and browser debugging requires context switching.|
| ❌ **4. Restrictions related to iframe still exist** | For example, isolation issues such as cross-domain cookies and localStorage still require special handling.|
| ❌ **5. The initial loading is still slower than the pure runtime solution** | The first loading of the sub-application still requires the creation of an iframe document, which is slightly slower than the micro-app.|
| ❌ **6. SSR support is incomplete** | Unbounded is currently mainly oriented to SPA mode and has weak SSR support.|
| ❌ **7. Relies on a lot of DOM operations** | A large number of internally dynamically injected scripts and styles may cause performance fluctuations in complex scenarios.|



##### 🧭 5. Suggestions for applicable scenarios {#🧭-五、适用场景建议}

✅ **Recommended circumstances for using Wujie:**

* Enterprise-level backend/platform system;
* There are many sub-applications (>5), and the technology stack is not unified;
* Need strong isolation but don’t want to sacrifice performance;
* I hope to reuse the existing system without major changes.

⚠️ **Case in which Wujie is not recommended:**

* Pursue the ultimate performance (the first screen is extremely short);
* Simple internal system (only 2 to 3 sub-projects);
* Want SSR isomorphic rendering;
* The team has limited manpower (higher debugging and maintenance costs).


##### 💬 6. Summarize in one sentence {#💬-六、总结一句话}

> **Wujie is a "balanced micro front-end framework" between `iframe` and `qiankun`:**
>
> With the security of iframe + the performance and flexibility of qiankun,
> Suitable for large-scale, multi-technology stack, and long-life-cycle front-end platform projects.
