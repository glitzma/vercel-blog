## 一、为什么 WebAssembly 在安全上“看起来很危险”？ {#一、为什么-webassembly-在安全上-看起来很危险}

先直觉判断：

| 特性     | 安全风险   |
| ------ | ------ |
| 接近原生速度 | 类似本地代码 |
| 显式内存   | 容易越界   |
| 可被编译   | 难静态分析  |
| 常来自第三方 | 供应链风险  |

👉 **如果 Wasm 能随便访问系统，浏览器安全直接崩溃**

所以：

> **Wasm 从设计之初就是“被关在笼子里的原生代码”**


## 二、Chrome 中 Wasm 的整体安全位置 {#二、chrome-中-wasm-的整体安全位置}

```
操作系统
  ↑
Chrome OS Sandbox
  ↑
Renderer Process
  ↑
V8 Wasm Engine
  ↑
WebAssembly Module
```

👉 Wasm **并没有更高权限**
👉 它只是 **Renderer 里的一个执行引擎**


## 三、第一道防线：进程级隔离（Chrome） {#三、第一道防线-进程级隔离-chrome}

### 1️⃣ Wasm 跑在哪？ {#_1️⃣-wasm-跑在哪}

* **Renderer Process**
* 与 JS 同级
* 受 **Site Isolation** 保护

```text
bank.com Wasm → Renderer A
evil.com Wasm → Renderer B
```

即使 Wasm 被攻破：

* 不能跨站
* 不能访问 OS


### 2️⃣ OS 级沙箱 {#_2️⃣-os-级沙箱}

Renderer 进程：

* 不能读写任意文件
* 不能调用系统 API
* 不能执行系统指令

👉 **Wasm 没有“系统调用”概念**


## 四、第二道防线：Wasm 的语言级安全模型 ⭐⭐⭐⭐⭐ {#四、第二道防线-wasm-的语言级安全模型-⭐⭐⭐⭐⭐}

这是 Wasm **最核心的安全点**。


### 1️⃣ 没有“任意指针” {#_1️⃣-没有-任意指针}

```c
int* p = (int*)0xdeadbeef; // ❌ Wasm 中不存在
```

Wasm：

* 只有 **线性内存（Linear Memory）**
* 地址 = 偏移量


### 2️⃣ 线性内存模型 {#_2️⃣-线性内存模型}

```
Linear Memory
 ├── 0x0000
 ├── ...
 ├── 0x10000
```

线性内存访问必须符合整体边界约束：

* 超出线性内存区域的访问会 trap；可通过检查、保护页等机制保证语义。
* 区域内相邻对象仍可能被越界覆盖，C/C++ 缓冲区错误或 use-after-free 不会自动消失。

👉 **宿主隔离不等于应用对象级内存安全**。
👉 **合法指令不能任意访问 Renderer 内存或 JS Heap；引擎漏洞是另一层风险**。


### 3️⃣ 不可执行数据（W^X） {#_3️⃣-不可执行数据-w-x}

* Wasm 内存 ≠ 可执行
* Code Space 与 Data Space 分离

👉 防止：

* shellcode 注入
* JIT spraying


### 4️⃣ 模块验证（Validation） {#_4️⃣-模块验证-validation}

Wasm 在执行前：

* 先验证字节码
* 控制流合法
* 类型正确
* 栈平衡

```text
非法模块 → 拒绝加载
```


## 五、第三道防线：V8 Wasm 引擎 {#五、第三道防线-v8-wasm-引擎}

### 1️⃣ 编译流程 {#_1️⃣-编译流程}

```
Wasm Binary
  ↓
Decoder & Validator
  ↓
Liftoff（baseline compiler）
  ↓
TurboFan（优化编译）
```

#### 安全策略 {#安全策略}

<span id="_2️⃣-边界检查永不移除-关键"></span>


* 先快编译
* 再安全优化
* 随时可回退


### 2️⃣ 保留线性内存边界语义 {#_2️⃣-保留线性内存边界语义}

即使经过优化：

* 必须维持越界访问 trap 的语义。
* 可证明安全时可以消除冗余显式检查，或采用保护页；语义要求不等于每次访问都有显式检查。


### 3️⃣ 与 JS 的交互是“受控的” {#_3️⃣-与-js-的交互是-受控的}

Wasm **不能主动**：

* 访问 DOM
* 发网络请求
* 调用系统 API

只能：

```js
imported_function()
```

👉 JS 是 **能力代理（Capability Broker）**


## 六、第四道防线：能力模型（Capability-based Security） {#六、第四道防线-能力模型-capability-based-security}

> **Wasm 本身没有能力，能力来自宿主**

#### 举例 {#举例}

```js
const wasm = new WebAssembly.Instance(module, {
  env: {
    log: console.log
  }
})
```

Wasm 只能：

* 调用 `log`
* 不能调用 `alert`
* 不能访问 `document`

👉 这是**最强的安全模型之一**


## 七、Wasm vs JS：谁更危险？ {#七、wasm-vs-js-谁更危险}

| 维度 | JS | Wasm |
| ---- | ---------- | ------ |
| 内存模型 | 无任意地址访问语法，引擎仍可能有漏洞 | 隔离线性内存，但不保证内部对象安全，引擎也可能有漏洞 |
| 执行权限 | 受浏览器与宿主 API 限制 | 受宿主导入与浏览器策略限制 |
| 性能 | 依赖工作负载和优化 | 适合部分计算任务，需要测量 |
| 攻击面 | JS 引擎、DOM 与宿主 API | Wasm 引擎、导入函数和应用逻辑 |

不能仅凭语言名称比较安全性。Wasm 保护宿主边界，应用仍需安全语言、输入校验和资源管理。

[WebAssembly 官方内存安全说明](https://webassembly.org/docs/security/#memory-safety)。


## 八、Wasm 能攻击什么？不能攻击什么？ {#八、wasm-能攻击什么-不能攻击什么}

#### ❌ 不能 {#❌-不能}

* 绕过同源策略
* 访问 Cookie
* 操作 DOM
* 直接发请求
* 调系统 API

#### ⚠️ 可能的风险 {#⚠️-可能的风险}

* DoS（死循环）
* Spectre 侧信道（已缓解）
* 引擎实现漏洞；没有统计口径时不应断言其“极少”。


## 九、Wasm + CSP 安全策略 {#九、wasm-csp-安全策略}

```http
Content-Security-Policy:
  script-src 'self';
  object-src 'none';
```

⚠️ Wasm 受：

* `script-src`
* `wasm-unsafe-eval`（新）

```http
script-src 'self' 'wasm-unsafe-eval';
```

👉 默认更严格


## 十、真实攻击视角（非常重要） {#十、真实攻击视角-非常重要}

#### 攻击链（极难） {#攻击链-极难}

```
恶意 Wasm
 ↓
V8 Wasm JIT bug
 ↓
突破 Wasm sandbox
 ↓
突破 Renderer sandbox
 ↓
OS
```

👉 Chrome 安全目标：

> **让这条链几乎不可行**


## 十一、“WebAssembly 安全模型”终极答案 {#十一、-webassembly-安全模型-终极答案}

> 浏览器中的 WebAssembly 受同源策略、渲染器沙箱和宿主能力限制；模块验证和线性内存边界提供隔离，不保证内部对象安全。显式导入可提供宿主能力，应用缺陷、资源耗尽和引擎漏洞仍需考虑。
