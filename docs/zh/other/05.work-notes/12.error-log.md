## 1、前端监控概述与核心价值 {#_1、前端监控概述与核心价值}
前端监控是保障产品质量的“眼睛”。它能帮助你在用户投诉之前发现 Bug，在老板质疑之前量化性能瓶颈。


## 2. 监控的三个核心维度 (监控什么？) {#_2-监控的三个核心维度-监控什么}

一个完善的前端监控系统通常包含以下三个方面：

#### 🛡️ 稳定性监控 (Stability / Error) {#🛡️-稳定性监控-stability-error}
* **JS 错误:** 运行时报错（`TypeError`、`ReferenceError` 等）。
* **资源加载错误:** 图片、CSS、Script 加载失败（通常是 404）。
* **API 请求错误:** 接口返回 4xx/5xx，或者业务逻辑上的“成功但报错”（如 `{code: -1, msg: 'error'}`）。
* **白屏检测:** 页面关键 DOM 节点缺失，导致用户看到一片白，这是最高优先级的致命故障。

#### 🚀 性能监控 (Performance) {#🚀-性能监控-performance}
* **加载速度:** 页面多久能刷出来？多久能交互？
* **接口耗时:** 关键业务接口的响应时间。
* **静态资源:** 主要是大图、大 JS 文件的加载耗时。

#### 👥 用户行为监控 (User Behavior) {#👥-用户行为监控-user-behavior}
* **PV/UV:** 基础的访问量数据。
* **用户路径:** 用户点进了哪个页面，又跳转到了哪里。
* **点击热力图:** 用户最喜欢点哪里。
* **场景回溯 (Session Replay):** **这是排查 Bug 的神器**。通过技术手段（如 `rrweb`）录制用户操作视频，还原 Bug 发生时的真实场景。



## 3. 关键性能指标 (Core Web Vitals) {#_3-关键性能指标-core-web-vitals}

Core Web Vitals 的三项核心指标是 LCP、INP、CLS，通常按真实用户数据的第 75 百分位评估。FCP 是辅助加载指标。

| 指标 | 全称 | 中文含义 | 衡量什么？ | 标准（好） |
| :--- | :--- | :--- | :--- | :--- |
| **LCP** | Largest Contentful Paint | 最大内容绘制 | 视口内最大的合格图片或文本块出现的时间。 | ≤ 2.5s |
| **INP** | Interaction to Next Paint | 交互到下一次绘制 | 页面交互的整体响应表现。 | ≤ 200ms |
| **CLS** | Cumulative Layout Shift | 累积布局偏移 | 页面生命周期内布局的视觉稳定性，无时间单位。 | ≤ 0.1 |
| **FCP（辅助）** | First Contentful Paint | 首次内容绘制 | 首次绘制文本、图片等内容的时间，不保证业务页面已可用。 | ≤ 1.8s |


## 4. 工具选型方案 {#_4-工具选型方案}

根据团队规模和预算，通常有三种选择路径：

#### 💎 方案 A：SaaS 商业服务 (最省心，但贵) {#💎-方案-a-saas-商业服务-最省心-但贵}
适合中小团队或快速迭代期，花钱买时间。
* **Sentry:** 全球最强。错误追踪能力极强，支持 SourceMap 还原代码，现在的性能监控也做得很好。
* **LogRocket:** 专注于**会话回放**，能像看电影一样看用户怎么操作出错的，体验极佳。
* **阿里云 ARMS / 腾讯云 RUM:** 国内大厂方案，合规性好，网络接入快。

#### 🛠️ 方案 B：自研 / 基于开源搭建 (成本可控，数据私有) {#🛠️-方案-b-自研-基于开源搭建-成本可控-数据私有}
适合大厂或对数据隐私要求高的团队。
* **Web-Tracing:** 国内开发者的开源项目，功能比较全。
* **Prometheus + Grafana:** 后端常用的监控方案，前端通过埋点 SDK 上报数据，Grafana 做可视化面板。
* **Sentry (Self-hosted):** Sentry 提供私有化部署版本，但维护成本（服务器资源、数据库）较高。

#### 📦 方案 C：简单埋点 (轻量级) {#📦-方案-c-简单埋点-轻量级}
* **Google Analytics (GA4):** 免费，主要看流量和简单的性能数据，查 Bug 能力弱。
* **Lighthouse (本地):** 不是实时监控，但适合开发阶段跑分优化。


## 5. 核心技术实现与难点 {#_5-核心技术实现与难点}
### 5.1 白屏监控的实现方案 {#_5-1-白屏监控的实现方案}
#### ✅ 一、什么是白屏？ {#✅-一、什么是白屏}

白屏指页面加载后，用户看到几秒钟“什么都没有渲染”，常见原因：

* JS 报错导致根节点没挂载
* 资源加载失败（CSS/JS）
* 后端返回空 HTML
* 路由跳转异常（SPA）
* 渲染被长任务阻塞
* 第三方脚本卡住

白屏上报的核心：
**发现用户看到“全白”的画面并记录上下文信息。**


#### ✅ 二、白屏检测的 3 种实战方案（按可靠性排序） {#✅-二、白屏检测的-3-种实战方案-按可靠性排序}

##### **方案 1：关键 DOM 探测（推荐）** {#方案-1-关键-dom-探测-推荐}

<span id="✔-可直接用的代码"></span>


适用于能够定义业务就绪标记的页面；需要按页面内容和加载状态校准。

原理：
**判断首屏是否成功渲染关键内容**（主容器、关键节点、LCP 元素等）

###### ✔ 检测示例 {#✔-检测示例}

```js
(function () {
  const TIMEOUT = 5000;
  let lcp;
  let observer;

  if (typeof PerformanceObserver !== 'undefined' &&
      PerformanceObserver.supportedEntryTypes?.includes('largest-contentful-paint')) {
    observer = new PerformanceObserver(list => {
      for (const entry of list.getEntries()) lcp = entry.startTime;
    });
    observer.observe({ type: 'largest-contentful-paint', buffered: true });
  }

  setTimeout(() => {
    if (document.visibilityState !== 'visible') {
      observer?.disconnect();
      return;
    }

    const root = document.getElementById('app') || document.getElementById('root');
    // Mark meaningful business content, including empty or image-only views.
    const content = root?.querySelector('[data-page-ready="true"]');
    const rect = content?.getBoundingClientRect();
    const ready = rect && rect.width > 0 && rect.height > 0;

    if (!ready) {
      navigator.sendBeacon('/monitor/white-screen', JSON.stringify({
        type: 'suspected-white-screen',
        url: location.href,
        timestamp: Date.now(),
        performance: {
          fcp: performance.getEntriesByName('first-contentful-paint')[0]?.startTime ?? null,
          lcp: lcp ?? null
        }
      }));
    }
    observer?.disconnect();
  }, TIMEOUT);
})();
```

业务需要在有效内容上设置 `data-page-ready="true"`。超时未出现标记只说明疑似异常，需要结合加载状态和错误日志分析；LCP 是诊断上下文，不能证明页面始终正常。SPA 路由切换需单独检测，原始 LCP 不是每次路由切换的指标。


##### **方案 2：像素采样检测（更严格，但耗性能）** {#方案-2-像素采样检测-更严格-但耗性能}

`canvas.drawImage()` 不能直接绘制 `document.body`。需要先通过支持的截图或 DOM 渲染方案获得图像，再绘制到 canvas；跨源图像还可能限制像素读取。

若已有可读取截图，RGB 平均值应将三个通道之和除以像素数的三倍，范围为 0–255。还要采样多个区域、排除透明像素，并考虑深色主题、空状态和加载占位，不能只凭左上角 10×10 像素判定整屏。

截图和阈值分析需要额外实现及验证，此处不提供直接绘制 body 的伪截图代码。[drawImage 参数](https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/drawImage)。


##### **方案 3：超时 + DOM 无变化（轻量 fallback）** {#方案-3-超时-dom-无变化-轻量-fallback}

DOM 节点数未变化不等于白屏：静态页面、SSR 页面或文本更新都可能不改变节点数。超时后可记录节点数和业务就绪标记作为诊断数据，不能直接将“节点数未变化”判定为故障。


#### ✅ 三、白屏上报的数据格式（建议） {#✅-三、白屏上报的数据格式-建议}

**统一结构便于分析：**

```json
{
  "type": "white-screen",
  "url": "https://xxx.com/page",
  "timestamp": 1710000000000,
  "ua": "Mozilla/5.0 ...",
  "domCount": 4,
  "fcp": 2200,
  "lcp": 0,
  "stack": "Error stack if available",
  "network": {
    "rtt": 50,
    "downlink": 4
  },
  "htmlSample": "<html>..."
}
```


#### ✅ 四、如何减少误报？ {#✅-四、如何减少误报}

###### **1. 检查是否有 LCP** {#_1-检查是否有-lcp}

LCP 表明页面曾绘制过合格内容，但后续路由或渲染仍可能失败。通过 `PerformanceObserver` 获取它，不能用它单独排除白屏。

###### **2. 检查是否存在 skeleton（骨架屏）** {#_2-检查是否存在-skeleton-骨架屏}

骨架屏应作为“加载中”状态，在合理超时后检查业务内容；永久跳过带骨架屏的页面会漏掉加载卡死。

###### **3. 检查是否用户主动切走 tab** {#_3-检查是否用户主动切走-tab}

若页面被后台化，白屏检测应跳过：

```js
document.visibilityState === "visible"
```

###### **4. 分地域 + 设备聚合** {#_4-分地域-设备聚合}

低端设备白屏率高可能来自加载较慢、主线程阻塞或兼容性问题，需要结合数据排查。


#### ✅ 五、白屏监控仪表盘（指标建议） {#✅-五、白屏监控仪表盘-指标建议}

你可以在 Grafana/Sentry/Datadog 中做 3 个核心指标：

###### **1. 白屏率（主指标）** {#_1-白屏率-主指标}

<span id="_2-lcp-0-的比例-辅助指标"></span>


```
白屏次数 / PV
```

###### **2. 未采集到 LCP 的比例（区分未支持、隐藏页面和采集失败）** {#_2-未采集到-lcp-的比例-区分未支持、隐藏页面和采集失败}

###### **3. 白屏分布** {#_3-白屏分布}

* 终端：安卓 / iOS / 桌面
* 地域：省份 / 国家
* 网络：4G / WiFi
* 页面：URL pattern

这可以快速定位到具体场景。



白屏诊断流程
1. 看 RUM 数据：FCP/LCP/INP 及地域/设备分布，确定是否普遍或个别设备/地区问题。
2. 回放/filmstrip：用 Lighthouse lab filmstrip 或 RUM 视频/回放找出“最大元素什么时候出现”。（若 LCP 总是某张大图 → 优化该图）([web.dev][3])
3. 查看网络面板：是否资源被阻塞（CSS/JS/Fonts）或第三方慢。
4. 查看主线程：是否被长任务阻塞（导致渲染被延后）。
5. 施策（最快路径）：保证首屏 HTML 直接可渲染 + preload 关键资源 + 异步非关键 JS。


工具推荐（监控 + 本地调试）

* **RUM/监控**：Sentry / Datadog RUM / NewRelic Browser / 自建收集 + Grafana
* **本地/CI 测试**：Lighthouse（或 Lighthouse CI） + PageSpeed Insights + WebPageTest（filmstrip）
* **诊断**：Chrome DevTools（Performance 面板 + Lighthouse） + web-vitals（上报）([Chrome for Developers][2])



### 5.2 错误捕获与上报 {#_5-2-错误捕获与上报}

##### 跨域的js运行错误捕获 {#跨域的js运行错误捕获}

只能捕获错误但不能拿到具体信息

1. 在script标签增加crossorigin属性(在客户端做)		
2. 设置js资源响应头Access-Control-Allow-Origin: * （这里可以是*也可以是域名。需要在服务端做）		

##### 错误上报 {#错误上报}

1. 采用ajax通信方式上报（一般不用这种方式）		
2. 利用Image对象上报（如google的gaa，国内的cnzz都是image方式上报）		
3. 监听请求进行上报时可以重写xmlHttpRequest的方式，重写send函数，执行完上报，在用老的send函数call执行发送请求		

```js
export function injectXHR() {
    let XMLHttpRequest = window.XMLHttpRequest;
    let oldOpen = XMLHttpRequest.prototype.open;
    XMLHttpRequest.prototype.open = function (method, url, async, username, password) {
        if (!url.match(/logstores/) && !url.match(/sockjs/)) {
            this.logData = {
                method, url, async, username, password
            }
        }
        return oldOpen.apply(this, arguments);
    }
    let oldSend = XMLHttpRequest.prototype.send;
    let start;
    XMLHttpRequest.prototype.send = function (body) {
        if (this.logData) {
            start = Date.now();
            let handler = (type) => (event) => {
                let duration = Date.now() - start;
                let status = this.status;
                let statusText = this.statusText;
                tracker.send({//未捕获的promise错误
                    kind: 'stability',//稳定性指标
                    type: 'xhr',//xhr
                    eventType: type,//load error abort
                    pathname: this.logData.url,//接口的url地址
                    status: status + "-" + statusText,
                    duration: "" + duration,//接口耗时
                    response: this.response ? JSON.stringify(this.response) : "",
                    params: body || ''
                })
            }
            this.addEventListener('load', handler('load'), false);
            this.addEventListener('error', handler('error'), false);
            this.addEventListener('abort', handler('abort'), false);
        }
        oldSend.apply(this, arguments);
    };
}
```

### 5.3 性能数据采集 {#_5-3-性能数据采集}

1. **监测与回归防护*** 在 CI/PR 中加入 Lighthouse 或 PSI 检查（关注 LCP/FCP/INP 回归），并在发布后用 RUM 数据验证。
2. [PerformanceTiming](https://developer.mozilla.org/zh-CN/docs/Web/API/PerformanceTiming)对象包含延迟相关的性能信息
4. [PerformanceObserver.observe](https://developer.mozilla.org/zh-CN/docs/Web/API/PerformanceObserver/observe)方法用于观察传入的参数中指定的性能条目类型的集合。当记录一个指定类型的性能条目时，性能监测对象的回调函数将会被调用

- [DOMContentLoaded含义](https://developer.mozilla.org/zh-CN/docs/Web/API/Window/DOMContentLoaded_event)
- [FMP(First Meaningful paint)(首次有意义绘制)](https://docs.google.com/document/d/1BR94tJdZLsin5poeet0XoTW60M0SjvOJQttKT-JK8HI/view#)

```js
// 安装：npm i web-vitals
import {onLCP, onFCP, onCLS, onINP} from 'web-vitals';

function sendMetric(name, value, extra = {}) {
  navigator.sendBeacon('/rum/metric', JSON.stringify({name, value, extra, url: location.href, ts: Date.now()}));
}

onLCP(metric => sendMetric('LCP', metric.value));
onFCP(metric => sendMetric('FCP', metric.value));
onCLS(metric => sendMetric('CLS', metric.value));
onINP(metric => sendMetric('INP', metric.value));
```
示例使用 `web-vitals` 的 `onLCP`、`onFCP`、`onCLS`、`onINP` API；安装时锁定版本并检查导出，服务端仍需正确聚合真实用户数据。[官方用法](https://github.com/GoogleChrome/web-vitals#usage)。


### 5.4 实施难点与解决方案（SourceMap、采样、过滤）落地实施的难点与技巧 {#_5-4-实施难点与解决方案-sourcemap、采样、过滤-落地实施的难点与技巧}

如果你准备开始做监控，注意以下几个“坑”：

1.  **SourceMap 安全问题:**
    * 线上报错通常是压缩后的代码（如 `a.js:1:503`），看不懂。
    * **解决:** 需要在构建流程（CI/CD）中把 `.map` 文件上传到监控平台（如 Sentry），但**绝对不要**部署到公网服务器上，否则源码会泄露。

2.  **海量日志削峰:**
    * 如果某个 Bug 导致无限循环报错，瞬间上万条日志会打爆服务器或耗尽 SaaS 配额。
    * **解决:** 前端 SDK 必须做**采样 (Sampling)** 和 **防抖 (Throttle)**。例如：同一个错误 1 秒内只报 1 次，或者只采集 10% 的性能数据。

3.  **无意义的报错:**
    * `Script error.` (跨域脚本错误) 或 浏览器插件注入的错误。
    * **解决:** 配置过滤规则（Ignore List），忽略非业务域名的脚本错误和常见的插件错误。

## 7. 参考资料与扩展阅读 {#_7-参考资料与扩展阅读}

### Web Vitals {#web-vitals}

- TTFB(time to first byte)(首字节时间)	是指浏览器发起第一个请求到数据返回第一个字节所消耗的时间，这个时间包含了网络请求时间、后端处理时间
- FP(First Paint)(首次绘制)	首次绘制包括了任何用户自定义的背景绘制，它是将第一个像素点绘制到屏幕的时刻
- FCP（First Contentful Paint）首次内容绘制：首次绘制文本、图片或 SVG 等合格内容的时间，不保证业务页面已就绪。
- [FMP(First Meaningful paint)(首次有意义绘制)](https://docs.google.com/document/d/1BR94tJdZLsin5poeet0XoTW60M0SjvOJQttKT-JK8HI/view)	首次有意义绘制是页面可用性的量度标准
- INP（Interaction to Next Paint）交互到下一次绘制：反映页面生命周期内点击、触摸和键盘交互的响应表现，包含输入延迟、处理时间和呈现延迟。
- [LCP	(Largest Contentful Paint)(最大内容渲染)](https://wicg.github.io/largest-contentful-paint/)	代表在viewport中最大的页面元素加载的时间。`2.5s`以内是好的，2.5s到4s需要优化。
- DCL	(DomContentLoaded)(DOM加载完成)	当 HTML 文档被完全加载和解析完成之后,DOMContentLoaded 事件被触发，无需等待样式表、图像和子框架的完成加载
- L	(onLoad)	当依赖的资源全部加载完毕之后才会触发
- TTI	(Time to Interactive) 可交互时间	用于标记应用已进行视觉渲染并能可靠响应用户输入的时间点
- FID（First Input Delay）首次输入延迟：首次交互发生到事件处理开始的等待时间；这是历史指标，现已由 INP 取代为核心指标。
- TBT（Total blocking time）主线程累计阻塞时间
- CLS（Cumulative Layout Shift）累积布局偏移，是无时间单位的分数：≤ 0.1 为好，> 0.1 且 ≤ 0.25 需要改善。[指标说明](https://web.dev/articles/cls)。
- 卡顿	超过50ms的长任务。响应用户交互的响应时间如果大于100ms,用户就会感觉卡顿
- [paint timing](https://w3c.github.io/paint-timing/)
