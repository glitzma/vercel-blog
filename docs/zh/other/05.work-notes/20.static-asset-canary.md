## 🔵 静态资源灰度发布（Canary Release for Static Assets） {#🔵-静态资源灰度发布-canary-release-for-static-assets}

让部分用户获得新版 HTML，其他用户继续获得旧版。关键是**稳定分流、资源版本固定、保留旧资源与可回滚**。下面统一使用 Nginx、持久化用户 Cookie 和版本目录说明。

## ⭐ 方案 1：Nginx / CDN 分流（最常用、最稳定） {#⭐-方案-1-nginx-cdn-分流-最常用、最稳定}

<span id="⛳-思路"></span>
<span id="🔧-nginx-配置示例-按-cookie-分流"></span>
<span id="用法"></span>
<span id="优点"></span>


分流发生在 HTML 入口，使用稳定用户标识或首次访问生成的 Cookie；不能每个请求重新随机分组。资源使用版本 URL，已打开页面始终请求相应版本。

## ⭐ 方案 2：CDN 边缘规则灰度（企业常用，如阿里云、Cloudflare） {#⭐-方案-2-cdn-边缘规则灰度-企业常用-如阿里云、cloudflare}

<span id="示例-cloudflare-worker-php-rule"></span>


CDN/边缘函数可实现相同逻辑，需核对产品能力。HTML 应绕过共享缓存或按版本分区，不能将一个用户的入口缓存给所有人；静态资源按版本 URL 共享缓存。

## ⭐ 方案 3：HTML 层 AB Test（适用于 SPA） {#⭐-方案-3-html-层-ab-test-适用于-spa}

<span id="⛳-思路-1"></span>


HTML 引用 `/releases/v1/js/app.hash.js` 或 `/releases/v2/js/app.hash.js`。动态 import、CSS 中图片和字体也要遵循相同 base/publicPath。

## ⭐ 方案 4：单页应用内部版本切换（有限场景） {#⭐-方案-4-单页应用内部版本切换-有限场景}

内部加载其他模块版本需处理运行状态、共享依赖和重复初始化。完整 SPA 通常在 HTML 入口选择版本；服务端回滚不会自动切换已运行页面。

## ⭐ 方案 5：`CI/CD` 流程灰度 {#⭐-方案-5-ci-cd-流程灰度}

先部署完整资源，再开放少量用户，观测后扩大比例。回滚改变新入口选择，保留已打开页面需要的资源。

## 🔵 Vue 项目静态资源灰度发布（完整可落地案例） {#🔵-vue-项目静态资源灰度发布-完整可落地案例}

<span id="📌-场景"></span>


以下构建针对 Vue CLI；Vite 使用对应 base 设置。v1/v2 是示意名称，每次发布使用不可变版本，不能覆盖已长期缓存的资源。[publicPath](https://cli.vuejs.org/config/#publicpath)。

### 第一步：构建产物做版本隔离 {#第一步-构建产物做版本隔离}

<span id="🔧-build-脚本-package-json-加-version-参数"></span>


`vue.config.js`：

```js
const version = process.env.APP_VERSION || 'v1';
if (!/^v[0-9]+$/.test(version)) throw new Error('Invalid release version');
module.exports = {
  publicPath: '/releases/' + version + '/',
  outputDir: 'dist/' + version
};
```

```bash
APP_VERSION=v1 npx vue-cli-service build
APP_VERSION=v2 npx vue-cli-service build
```

### 第二步：服务器结构 {#第二步-服务器结构}

```text
/var/www/my-app/releases/
  v1/index.html
  v1/js/app.<hash>.js
  v1/css/app.<hash>.css
  v2/index.html
  v2/js/app.<hash>.js
  v2/css/app.<hash>.css
```

### 第三步：Nginx 灰度配置（核心） {#第三步-nginx-灰度配置-核心}

<span id="🔧-nginx-配置-可直接复制"></span>
<span id="✔-说明"></span>
<span id="第四步-给灰度用户注入-cookie"></span>


以下放在 http 上下文，示例 8080 端口用于本地验证。生产用实际域名和 HTTPS，并为 Cookie 加 Secure。Cookie 只用于灰度，不作为权限凭证。

```nginx
map $cookie_gray_id $gray_seed {
    "~^[0-9a-f]{32}$" $cookie_gray_id;
    default $request_id;
}
map $cookie_gray_id $gray_seed_cookie {
    "~^[0-9a-f]{32}$" "";
    default "gray_id=$gray_seed; Path=/; Max-Age=2592000; HttpOnly; SameSite=Lax";
}
# Included exactly once in the http context.
include /etc/nginx/gray-split.conf;
map $cookie_version $version {
    v1 v1;
    default $gray_candidate;
}
server {
    listen 8080;
    server_name localhost;
    location ~ ^/releases/v[0-9]+/index\.html$ {
        root /var/www/my-app;
        try_files $uri =404;
        add_header Cache-Control "no-store" always;
    }
    location /releases/ {
        root /var/www/my-app;
        try_files $uri =404;
        add_header Cache-Control "public, max-age=31536000, immutable";
    }
    # SPA entry only; real applications need separate API/proxy locations.
    location / {
        root /var/www/my-app/releases/$version;
        try_files /index.html =404;
        add_header Cache-Control "no-store" always;
        add_header Set-Cookie $gray_seed_cookie always;
    }
}
```

`/etc/nginx/gray-split.conf` 初始内容：

```nginx
split_clients "$gray_seed:release-v2" $gray_candidate {
    10% v2;
    *   v1;
}
```

split_clients 哈希整个稳定标识并覆盖全部输入，不截取 request_id 的十六进制末位。首次 HTML 设置 gray_id 后沿用；百分比是哈希空间占比，实际用户数有采样波动。禁用 Cookie 或多个首次请求时分组可能变化，但资源 URL 仍固定版本。[split_clients](https://nginx.org/en/docs/http/ngx_http_split_clients_module.html)。

### 第五步：回滚方案（非常重要） {#第五步-回滚方案-非常重要}

<span id="❌-发现问题-一键回滚"></span>
<span id="第六步-ci-cd-自动化-可选"></span>
<span id="🟢-最终效果"></span>


全量映射到 v1，执行 `nginx -t` 后 reload。已打开的 v2 页面和懒加载仍可能请求 v2，不能立即删除目录；保留期应覆盖页面会话、缓存和 Service Worker 使用周期。

```nginx
split_clients "$gray_seed:release-v2" $gray_candidate {
    * v1;
}
```

## 🔵 灰度自动化脚本 {#🔵-灰度自动化脚本}

<span id="🟦-1-nginx-分流方案-基于随机数灰度"></span>
<span id="🟦-2-灰度脚本-gray-sh-支持-0–100-任意比例"></span>
<span id="🟦-3-使用方式-非常简单"></span>
<span id="✔-灰度-10"></span>
<span id="✔-灰度提升到-30"></span>
<span id="✔-灰度-90"></span>
<span id="✔-全量-100"></span>
<span id="✔-关闭灰度-回滚-v1"></span>
<span id="🟦-4-日志查看-确认灰度比例"></span>
<span id="🟦-5-在-ci-cd中使用"></span>
<span id="🟢-最终效果-你已经具备"></span>


接受 0–100 整数，两个端点显式使用默认分支。文件须事先存在，脚本需要写入及 Nginx 操作权限；多个发布任务在 CI 中串行化。

```bash
#!/usr/bin/env bash
set -euo pipefail

percent=${1:-}
if [[ ! "$percent" =~ ^(0|[1-9][0-9]?|100)$ ]]; then
  echo "Usage: gray.sh <integer 0-100>" >&2
  exit 1
fi
conf=/etc/nginx/gray-split.conf
backup=$(mktemp)
pending=$(mktemp /etc/nginx/gray-split.conf.XXXXXX)
trap 'rm -f "$backup" "$pending"' EXIT
cp "$conf" "$backup"
{
  echo 'split_clients "$gray_seed:release-v2" $gray_candidate {'
  if (( percent == 0 )); then
    echo '    * v1;'
  elif (( percent == 100 )); then
    echo '    * v2;'
  else
    echo "    $percent% v2;"
    echo '    * v1;'
  fi
  echo '}'
} > "$pending"
# Keep the existing file permissions.
cat "$pending" > "$conf"
if ! nginx -t; then
  cat "$backup" > "$conf"
  echo "Invalid configuration; restored previous file" >&2
  exit 1
fi
if ! nginx -s reload; then
  cat "$backup" > "$conf"
  nginx -s reload || true
  echo "Reload failed; restored previous file" >&2
  exit 1
fi
echo "Configured canary hash-space share: $percent%"
```

```bash
bash gray.sh 15
bash gray.sh 100
bash gray.sh 0
```

分别配置 15%、全量和回滚。恢复 Cookie 会临时选择 v1，这些用户不计入正常分桶比例；提升比例需由观测结果决定。

## 🔵 灰度失败 → 自动降级到稳定版本 {#🔵-灰度失败-→-自动降级到稳定版本}

<span id="🟦-一、核心思路"></span>
<span id="🟦-二、nginx-分流-前提"></span>
<span id="🟦-三、前端自动降级脚本-放在-index-html-顶部"></span>
<span id="🟦-四、降级的工作原理"></span>
<span id="_1-设置降级标记-避免无限-reload"></span>
<span id="_2-切换-cookie"></span>
<span id="_3-立即刷新页面-→-加载稳定版本-v1"></span>
<span id="🟦-五、确保不会无限循环-防止死循环"></span>
<span id="🟦-六、额外增强-捕获-js-runtime-白屏错误"></span>
<span id="🟦-七、额外增强-捕获未捕获-promise-错误"></span>
<span id="🟢-最终你拥有的能力"></span>


放在两个版本 HTML 的入口资源之前，只处理指定版本的 script/link 加载失败；不能保证消除所有白屏，也不应将任意业务异常视为回滚理由。

```html
<script>
(function () {
  const failedVersion = 'v2';
  const retryKey = 'gray_retry:' + failedVersion;
  window.addEventListener('error', function (event) {
    const target = event.target;
    if (!target || !['SCRIPT', 'LINK'].includes(target.tagName)) return;
    const resource = target.src || target.href;
    if (!resource) return;
    const url = new URL(resource, location.href);
    if (url.origin !== location.origin ||
        !url.pathname.startsWith('/releases/' + failedVersion + '/')) return;
    try {
      if (sessionStorage.getItem(retryKey)) return;
      sessionStorage.setItem(retryKey, 'done');
    } catch {
      return; // Storage unavailable: avoid uncontrolled reload loops.
    }
    document.cookie = 'version=v1; Path=/; Max-Age=3600; SameSite=Lax';
    location.reload();
  }, true);
})();
</script>
```

动态 import 失败需在调用处捕获，关键初始化失败结合框架钩子与业务状态决定恢复。稳定版也可能失败，仍需错误页和排查路径；每次发布更新版本与重试键。

## 🔥 关键注意点 {#🔥-关键注意点}

<span id="_1-必须使用带-hash-的构建产物"></span>
<span id="_2-旧版本资源必须继续保留"></span>
<span id="_3-index-html-才是灰度的关键"></span>
<span id="🟢-给你一个非常简短易记的总结"></span>


1. 检查入口、动态 chunk、CSS 图片和字体 URL 都包含发布版本。
2. 相同 gray_id 多次请求 HTML 应分组稳定；测试 0%、15%、100%，小样本无需恰好符合比例。
3. 测试 `/releases/v1/` 和 `/releases/v2/` 的已知资源、缓存头及缺失资源 404。
4. SPA 深链接返回 HTML，API 单独路由；CDN 不共享分流 HTML，Service Worker 不使用过期入口。
5. 模拟 v2 入口资源失败，最多尝试一次恢复；回滚后保留旧页面需要的资源。
