> **min-content 是内容相关的固有尺寸，可能需要测量，也可能复用缓存；其成本取决于上下文。**

## 一、什么是 min-content（从引擎角度） {#一、什么是-min-content-从引擎角度}

规范定义：

> min-content width = 内容在“不发生可避免溢出”的最小宽度

简单说：

```css
width: min-content;
```

等价于：

```text
把内容压缩到极限，但不能破坏内容本身
```

例如：

```html
<div>supercalifragilisticexpialidocious</div>
```

min-content width = 这个最长单词的宽度

因为不能断开。

## 二、为什么这会导致性能问题？ {#二、为什么这会导致性能问题}

关键：

> 浏览器无法直接知道 min-content width
> 缓存不可用时，可能需要分析相关子树和文本的不可断开片段。

有效缓存、明确尺寸和布局包含等条件可能减少重复工作。

可能涉及：

```text
layout subtree
→ measure text
→ measure inline fragments
→ measure replaced elements
→ measure nested containers
```

这是完整 layout 流程的一部分。

## 三、LayoutNG 中的真实计算流程 {#三、layoutng-中的真实计算流程}

下面的函数名仅表示固有尺寸计算的概念，不对应某个版本的公开 API：

```cpp
ComputeMinContentContribution()
```

流程近似：

```cpp
for child in children:
   if child is text:
       measure all words
       find longest unbreakable segment

   if child is element:
       recursively compute min-content

return max(child contributions)
```

注意：

> 这是递归的

复杂度：

```text
概念示意：成本取决于实际访问的内容和缓存
```

上述伪代码仅用于说明内容依赖，不是浏览器实现的精确复杂度证明。

## 四、何时可以复用缓存 {#四、为什么不能缓存}

固有尺寸可以缓存。内容、字体、断行规则、书写模式以及相关约束发生变化时，缓存可能失效；是否重算以及范围取决于实现。

不能仅凭父容器从 500px 变为 501px，就断言 min-content 完全改变或必须重新测量整个子树。

## 五、固有尺寸测量与最终布局 {#五、min-content-会强制-intrinsic-sizing-pass}

固有尺寸计算和最终布局相关但不相同；需要的测量次数取决于约束、内容与缓存。不能假定使用 min-content 就一定额外执行一次完整子树布局。

## 六、Flexbox 中的内容尺寸约束 {#六、flexbox-中-min-content-是性能炸弹的真正原因}

确定 flex base size 时，flex-basis:auto 会先参考主尺寸属性；只有在相应条件下才走内容尺寸计算。自动最小尺寸、min/max 约束也会影响最终结果，不是无条件同时计算 min-content 和 max-content。

## 七、最坏情况：嵌套 Flex + min-content {#七、最坏情况-嵌套-flex-min-content}

结构：

```html
flex
 └ flex
    └ flex
       └ text
```

计算：

外层 flex 需要：

```text
min-content of child flex
```

child flex 需要：

```text
min-content of its child flex
```

递归到底。

复杂度：

```text
嵌套深度和重复测量可能增加工作量
```

极端情况：

具体增长需要结合缓存和约束验证

## 八、真实例子：为什么一个长字符串会卡页面？ {#八、真实例子-为什么一个长字符串会卡页面}

例如：

```html
<div style="display:flex">
  <div style="flex:1">
    supercalifragilisticexpialidocious...
  </div>
</div>
```

浏览器必须：

```text
measure entire string
find break opportunities
calculate glyph widths
```

这涉及：

```text
font engine
text shaping engine
unicode break iterator
```

这是昂贵操作。

不是简单 strlen()

## 九、比普通 width:100px 慢多少？ {#九、比普通-width-100px-慢多少}

固定 width：

```css
width:100px;
```

浏览器：

```text
直接使用 100px
明确宽度可能简化尺寸确定，但排版和绘制其中的文本仍需要工作。
```

min-content：

```text
layout subtree
measure text
compute intrinsic size
```

不能在没有相同页面的测量结果时给出固定倍数。

## 十、LayoutNG 已经优化了什么？ {#十、layoutng-已经优化了什么}

LayoutNG 优化包括：

#### 优化 1：缓存 intrinsic size {#优化-1-缓存-intrinsic-size}

避免重复测量相同 constraint

但命中率有限。

#### 优化 2：避免不必要 intrinsic pass {#优化-2-避免不必要-intrinsic-pass}

如果：

```css
flex-basis: 0;
```

浏览器：

```text
可减少部分基准尺寸测量，但自动最小尺寸等约束仍可能依赖内容。
```

性能大幅提升。

#### 优化 3：fragment reuse {#优化-3-fragment-reuse}

避免重复 layout 子树

但 intrinsic sizing 仍然需要计算。

## 十一、如何记录性能对比 {#十一、性能对比-真实趋势}

原文的 8ms、25ms、40ms 没有对应实验，已撤回。请使用相同节点、字体、内容和视口，分别记录零基准、自动基准与 min-content 场景的 Layout 时间和 trace，不预设排名。

## 十二、最隐蔽的性能杀手组合 {#十二、最隐蔽的性能杀手组合}

```css
flex: 1 1 auto;
white-space: nowrap;
```

这会强制：

```text
max-content calculation
min-content calculation
```

非常昂贵。

## 十三、如何避免 min-content 性能问题（核心优化） {#十三、如何避免-min-content-性能问题-核心优化}

最重要优化：

### 优化 1（最有效） {#优化-1-最有效}

不要用：

```css
flex: 1 1 auto;
```

使用：

```css
flex: 1 1 0;
```

原因：

零基准不等于完全不做固有尺寸测量；必要时还需按产品布局检查 min-width、溢出和内容可读性。

是否改善性能及改善多少，应通过同一页面的测量决定。

### 优化 2 {#优化-2}

避免：

```css
width: min-content;
```

使用：

```css
width: 200px;
```

或

```css
flex-basis: 0;
```

### 优化 3 {#优化-3}

避免深层嵌套 flex

### 优化 4 {#优化-4}

避免：

```css
white-space: nowrap;
```

在 flex 子元素中滥用

## 十四、本质总结 {#十四、本质总结}

min-content 慢不是因为 LayoutNG 不够优化，

而是因为：

> min-content 依赖内容和格式化规则，缓存与明确约束可能减少重复分析。

它本质上是：

```text
content-dependent sizing
```

而不是：

```text
constraint-dependent sizing
```

constraint-dependent sizing 是快的。

content-dependent sizing 是慢的。

## 十五、终极理解 {#十五、终极理解}

明确尺寸的示例：

```css
width: 100px;
flex-basis: 0;
```

内容驱动尺寸的示例：

```css
width: min-content;
flex-basis: auto;
```

因为：

前者：

```text
可能减少部分固有尺寸确定工作
```

后者：

```text
可能需要内容分析；不代表每次完整遍历子树
```
