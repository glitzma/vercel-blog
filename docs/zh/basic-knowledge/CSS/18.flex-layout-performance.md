下文流程用于解释可能的布局成本，不代表每次布局的固定轮数或复杂度。性能取决于内容、约束、缓存和浏览器实现，应通过实际页面的 trace 验证。

## 一、浏览器渲染流程回顾（性能前提） {#一、浏览器渲染流程回顾-性能前提}

无论是 Flex 还是其他布局，性能都绕不开浏览器渲染流程：

1. **Parse HTML → DOM**
2. **Parse CSS → CSSOM**
3. **DOM + CSSOM → Render Tree**
4. **Layout（Reflow）**
5. **Paint**
6. **Composite**

⚠️ 影响性能最大的通常是：

* Layout（回流）
* Layout 触发链式计算
* 频繁强制同步布局

Flex 属于 **Layout 阶段的布局算法**，所以我们重点分析：

> Flex 的布局计算复杂度 + 回流传播范围 + 动态变化成本

## 二、Flex 布局底层算法成本 {#二、flex-布局底层算法成本}

Flex 是一种 **两阶段布局算法**（与 Block 不同）

### 1️⃣ 主轴尺寸计算（第一轮） {#_1️⃣-主轴尺寸计算-第一轮}

核心步骤：

1. 计算每个 flex item 的：

   * flex-basis
   * min/max
   * 内容尺寸（可能触发测量）
2. 计算总基准尺寸
3. 判断是否溢出
4. 分配 free space（grow 或 shrink）

如果涉及：

* auto
* content
* 百分比
* 未确定尺寸

浏览器必须：

👉 **先测量子元素内容尺寸**

这会触发：

* 子元素 layout
* 可能递归计算

#### 性能影响： {#性能影响}

复杂度接近：

```
成本随项目数量、内容测量和缓存命中情况变化
```

如果嵌套 Flex：

```
嵌套和重复测量可能增加成本，不能据此给出通用复杂度
```

### 2️⃣ 交叉轴对齐（第二轮） {#_2️⃣-交叉轴对齐-第二轮}

如果存在：

* align-items
* align-content
* stretch

浏览器可能需要：

👉 再跑一轮尺寸调整

尤其：

* 高度 auto
* 多行 wrap
* 垂直居中

这意味着：

> 主轴和交叉轴是算法中的不同步骤，不等于浏览器必定执行两轮完整布局。

## 三、为什么说 Flex 比 Block 更重？ {#三、为什么说-flex-比-block-更重}

传统 block 流：

```
从上到下顺序计算
普通块布局也可能需要内容测量、百分比解析或重新布局，不能视为总是单次计算。
```

Flex：

```
必须先算所有子元素 → 再统一分配空间
```

也就是说：

Block 是“单向流式”
Flex 是“整体协调式”

整体协调式 = 更多计算

## 四、性能瓶颈出现在哪些场景？ {#四、性能瓶颈出现在哪些场景}

### ❗ 1. 大量节点（列表） {#❗-1-大量节点-列表}

例如：

* 1000 个 flex item
* 每个 item 里面再嵌套 flex

可能出现：

* 多次回流
* 频繁测量
* 主线程占用高

对比：

* 简单 block 流性能更稳定

### ❗ 2. 动态改变 flex 属性 {#❗-2-动态改变-flex-属性}

例如：

```js
element.style.flex = "1";
```

会触发：

* 父容器重新计算
* 所有兄弟重新分配
* 子元素可能重新 layout

这是：

> 级联回流

### ❗ 3. 使用 auto / content / min-content {#❗-3-使用-auto-content-min-content}

例如：

```css
flex: 1 1 auto;
```

auto = 需要测量内容

测量内容 = layout

如果频繁 resize：

会非常耗性能

### ❗ 4. 嵌套 Flex 地狱 {#❗-4-嵌套-flex-地狱}

```html
flex
 └ flex
    └ flex
       └ flex
```

每一层都需要：

* 计算子尺寸
* 再回传给父级
* 再重新分配

理论上可能出现：

> 嵌套与相互依赖可能扩大布局工作量，具体成本需要测量。

## 五、Flex vs Grid 性能对比 {#五、flex-vs-grid-性能对比}

### 🔹 Grid

* 需要双轴计算
* 轨道尺寸算法也可能需要迭代与内容测量
* 不依赖内容尺寸时更快

### 🔹 Flex

* 更依赖内容尺寸
* 主轴分配更复杂
* 动态调整更频繁

#### 总结： {#总结}

| 场景     | 推荐           |
| ------ | ------------ |
| 单轴简单布局 | Flex         |
| 复杂二维布局 | Grid         |
| 超大列表   | Block + 虚拟滚动 |
| 高频动态变化 | 尽量避免 Flex    |

## 六、真实浏览器实现（以 Chromium 为例） {#六、真实浏览器实现-以-chromium-为例}

Chrome 使用：

* Blink Layout Engine
* 2020 后升级为 LayoutNG

Flex 在 LayoutNG 中：

* 使用约束求解模型
* 多轮测量
* 子树可能被重复访问

性能关键点：

* Constraint space 计算
* Fragment tree 构建
* Min/max content 测量

## 七、如何从性能角度优化 Flex？ {#七、如何从性能角度优化-flex}

### ✅ 1. 尽量避免 auto {#✅-1-尽量避免-auto}

替代：

```css
flex: 1 1 0;
```

而不是：

```css
flex: 1 1 auto;
```

flex-basis 为 0 可减少部分基准尺寸测量，但自动最小尺寸等约束仍可能要求测量内容。

### ✅ 2. 固定尺寸优于内容驱动 {#✅-2-固定尺寸优于内容驱动}

```css
width: 200px;
```

比：

```css
width: auto;
```

性能更稳定

### ✅ 3. 减少嵌套 {#✅-3-减少嵌套}

避免：

多层 flex 包裹

### ✅ 4. 使用 will-change（谨慎） {#✅-4-使用-will-change-谨慎}

仅在动画时使用：

```css
will-change: transform;
```

不要乱用，会增加内存

### ✅ 5. 使用 contain {#✅-5-使用-contain}

```css
contain: layout;
```

contain:layout 建立布局包含，但元素自身尺寸变化仍可能影响外部布局，不能当成绝对隔离。

非常有用

### ✅ 6. 虚拟滚动 {#✅-6-虚拟滚动}

大列表不要直接渲染：

* 1000 个 flex item
* 用虚拟列表

React/Vue 都有库支持

## 八、如何进行性能对比 {#八、性能实测-直观理解}

| 布局方式 | 需要记录的指标 |
| --- | --- |
| Block | Layout、Paint 与总耗时 |
| Flex 简单 | Layout、Paint 与总耗时 |
| Flex 嵌套 | Layout、Paint 与总耗时 |
| Grid 复杂 | Layout、Paint 与总耗时 |

记录浏览器版本、硬件、节点数、CSS、采样次数及 trace；不能只凭布局名称推断谁更快。

## 九、什么时候 Flex 性能不是问题？ {#九、什么时候-flex-性能不是问题}

实际上：

👉 在正常业务页面（几十个节点）

Flex 性能差异几乎可以忽略

真正成为问题的场景：

* 可视化大屏
* 数据看板
* 表格渲染
* 低端安卓设备
* 高频 resize

## 十、总结一句话 {#十、总结一句话}

Flex 的性能特点：

> 牺牲部分布局计算成本，换取极强的动态适配能力

它不是慢，而是：

* 计算更复杂
* 依赖内容
* 更容易触发多轮布局
