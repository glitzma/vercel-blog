# Git branch development workflow {#git分支开发工作流}

Documentation: [ Git branch development workflow ](https://git-scm.com/book/zh/v2/Git-分支-分支开发工作流)

### long term branch {#长期分支}

Because Git uses a simple three-way merge, it is not difficult to repeatedly merge one branch into another over a long period of time.In other words, you can have multiple open branches at different stages of the entire project development cycle; you can regularly merge certain topic branches into other branches.

Many developers who use Git like to work in this way. For example, **only keep completely stable code on the `master` branch**. The development process is in the `dev` branch. After development is completed, it is merged into the `test` branch for testing. Only the stable code that passes the test is merged into the `master` branch.

The `dev` and `test` branches do not need to remain absolutely stable, but after `test` reaches a stable state through testing, it can be merged into the `master` branch.

In fact, what we just discussed is a pointer that keeps moving to the right as you commit.The pointer to the stable branch (`master`) is always far behind in the commit history, while the pointer to the cutting-edge branch (`dev` or `test`) is often further ahead.

You can maintain different levels of stability this way.Some large projects also have a `proposed` (recommended) or `pu: proposed updates` (recommended updates) branch, which may not be able to enter the `master` branch because it contains some immature content.The purpose of this is to give your branches different levels of stability; when they have reached a certain level of stability, merge them into branches with a higher level of stability.Again, using multiple long-lived branches is not necessary, but it is often helpful, especially if you are working on a very large or complex project.

### Topic branches (short-term branches) {#主题分支-短期分支}

**Topic branches work for any size project** .Topic branching is a **short-term branch** , it is **Used to implement a single feature or its related work** 。

You already created the `iss53` and `hotfix` This usage has been seen in topic branches.The topic branch you used in the previous section ( `iss53` and `hotfix` branch), and after they were merged into the trunk branch, you deleted them.This technology allows you to quickly and completely context-switch - because your work is distributed among different pipelines, in different pipelines **Each branch is relevant only to its target feature** , therefore, **It will be easier to see what changes you made when doing things like code reviews** .You can keep your changes in a topic branch for minutes, days, or even months, waiting for them to mature before merging them, regardless of the order in which they were created or the progress of your work.

Consider an example where you work on the `master` branch to `C1`, then create a new `iss91` branch to solve a problem, and work on the `iss91` branch to `C4`. However, you have new ideas about that problem, so you create a new `iss91v2` branch to try to solve the problem in another way, and then you return to `master`After working on the branch for a while, you come up with an uncertain idea, so you create a new `dumbidea` branch in `C10` and do some experiments on it.Your commit history will look like this:

We will reveal more details about the branching workflow in [Distributed Git](https://git-scm.com/book/zh/v2/ch00/ch05-distributed-git), so please make sure you read that chapter before deciding what branching scheme to use for your next project.

Keep in mind that when you do so many operations, these branches are all local.When you create and merge branches, all of this happens within your local Git repository - there is no interaction with the server.
