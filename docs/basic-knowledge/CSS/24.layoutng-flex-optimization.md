This article explains LayoutNG through a constraint-and-fragment model; the diagrams do not imply a single computation pass. Figures without an original experiment are not performance evidence.

## 1\. Background: Why is LayoutNG needed? {#一、背景-为什么需要-layoutng}

Before 2020, Chrome used an older version of Blink Layout.

Question:

* Layout code 20+ years of historical baggage
* Block/Table/Flex/Grid are implemented individually
* Backflow propagation is uncontrollable
* Nested flex is prone to double calculations
* Floating point errors lead to repeated layout

To solve these problems, Chromium rewrote the layout engine:

> **LayoutNG**

It is the next generation layout system for Chromium/Blink.

Goal:

1. higher performance
2. Less repetitive layout
3. Predictable complexity
4. More precise specification implementation

## 2\. Performance issues with the old version of Flex {#二、旧版-flex-的性能问题}

There are mainly 4 types of problems with the old algorithm:

### 1️⃣ Repeated Measurement {#_1️⃣-重复测量-repeated-measurement}

In the old implementation:

* flex-basis:auto
* min-content
* shrink

will result in:

👉 Child elements are measured multiple times

The process is similar:

```
测量 → 分配空间 → 不够 → 重新测量 → 再分配
```

Nesting and repeated measurement may add cost, but growth depends on constraints and implementation rather than being universally exponential.

### 2️⃣ Backflow spread is uncontrollable {#_2️⃣-回流传播不可控}

In old Blink:

* Parent container size changes
* May trigger re-layout of all child elements
* Changes in child elements may affect parent elements

Form:

> Layout Ping-Pong

### 3️⃣ Non-uniform Layout Tree {#_3️⃣-不统一的-layout-tree}

In the old system:

* Block uses a set of logic
* Flex uses another set
* Table uses another set

Weak sharing ability → code duplication → difficulty in optimization

### 4️⃣ Floating point error problem {#_4️⃣-浮点误差问题}

Appears after space allocation:

* 1px offset
* reflow correction again

Resulting in additional layout passes

## 3\. The core design ideas of LayoutNG {#三、layoutng-的核心设计思想}

LayoutNG introduces three core structures:

### 1️⃣ Constraint Space (constraint space) {#_1️⃣-constraint-space-约束空间}

Core idea:

> Child elements no longer "guess their own size"
> Instead, the parent element gives a clear constraint space

It contains:

* available width
* Available height
* writing mode
* min/max

This way:

The child element layout is a pure function:

```
输入：Constraint Space
输出：Fragment
```

#### Performance implications: {#性能意义}

* Avoid repeated measurements
* Results can be reused for matching constraints when cache-validity conditions hold
* Results can be cached

### 2️⃣ Fragment Tree {#_2️⃣-fragment-tree-片段树}

The old version of layout directly modifies the render tree.

LayoutNG：

* Do not modify nodes directly
* Generate fragment
* All layout results are written to the fragment tree

Benefits:

* Does not contaminate the original structure
* Can be rolled back
* Can be cached
* Avoid repeated DOM traversal

### 3️⃣ One-way data flow {#_3️⃣-单向数据流}

Old version:

```
父 → 子
子 → 父
父再 → 子
```

LayoutNG：

```
父传约束 → 子返回结果
结束
```

Separating constraints from results helps reasoning and caching without eliminating sizing iterations.

This should not be equated with neural-network attention; the problems and constraints differ.

## 4\. How does LayoutNG optimize Flex? {#四、layoutng-如何优化-flex}

Now to the important points.

## 1️⃣ Reduce the number of measurements {#_1️⃣-减少测量次数}

Old version:

```
for each item:
   measure min-content
   measure max-content
```

LayoutNG：

* Only measure when you really need to
* Result caching
* Constraint is the same and can be reused directly

Equivalent to:

```
memoization
```

Caching and avoiding repeated work can improve specific pages, but do not establish a universal complexity reduction.
## 2️⃣ Smarter Free Space allocation algorithm {#_2️⃣-更聪明的-free-space-分配算法}

Flex grow/shrink is the most complicated part.

LayoutNG does:

* Precompute frozen items
* Allocation in batches
* Avoid repeated rollbacks

Older versions may:

```
分配 → 溢出 → 回退 → 再分配
```

New version:

```
分配空间 → 检查 min/max 约束 → 必要时冻结项目并迭代
```

Constraint handling may still require multiple distribution iterations; a single pass is not guaranteed.

## 3️⃣ Avoid nested explosion {#_3️⃣-避免嵌套爆炸}

Old version nesting:

```
Flex
 └ Flex
    └ Flex
```

The subtree is re-layout at each level.

LayoutNG：

* Subtree layout results are encapsulated as Fragment
* The parent layer only reads the dimensions
* Do not re-expand subtree

This greatly reduces nesting costs.

## 4️⃣ More accurate Dirty marking {#_4️⃣-更精准的-dirty-标记}

The dirty granularity of the old system is coarse:

```
一个属性变 → 整个 subtree layout
```

LayoutNG：

* Accurately record affected nodes
* Use LayoutInvalidationReason
* Only relayout necessary nodes

For example:

Change the margin of a flex item:

Only affects:

* the item
* The flex container

instead of the entire page

## 5️⃣ Improve min/max content calculation {#_5️⃣-改进-min-max-content-计算}

min-content is a Flex performance killer.

LayoutNG：

* Use unified intrinsic sizing algorithm
* Avoid repeated measurements
* Use higher precision float operations

Reduce the number of reflows.

## 5. Evidence needed for performance claims {#五、性能对比-真实趋势}

The previous comparison table and figures such as 20%–40% and 2x lacked original test sources and have been withdrawn; they should not be attributed to Chromium as general findings.

Fix the browser, content, and constraints; compare layout counts, duration, and cache reuse, and retain traces. Architectural improvements and speedups on a particular page require different evidence.

## 6\. A key breakthrough in LayoutNG {#六、layoutng-的一个关键突破}

It turns Layout into:

> "Functional Layout System"

```
Layout(node, constraint) → fragment
```

No side effects

This means:

* Easier to parallelize (future)
* Easier to cache
* easier to debug

## 7\. Why is Flex no longer a performance black hole? {#七、为什么现在-flex-不再是性能黑洞}

Because:

1. one-way constrained flow
2. Fragment caching
3. precise invalidation
4. Avoid multiple rounds of shrink/grow
5. Unify intrinsic calculations

Flex is still heavier than block,

But already:

> From "uncertain complexity" to "predictable complexity"

## 8\. How can you verify? {#八、你可以如何验证}

Open Chrome DevTools:

Performance → Record

Look:

* Layout time
* Layout invalidation
* Forced reflow

You will find:

The number of Flex layouts in modern Chrome is significantly less than in pre-2018 versions.

## 9\. Final summary {#九、终极总结}

Old version of Blink Flex:

> State driven + two-way propagation + multi-round measurement

LayoutNG Flex：

> Constraint-driven + one-way data flow + functional output

This is an architecture-level optimization.
